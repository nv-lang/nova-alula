# Alula: specification of the language for writing state machines as tables, version 2.22

Translation of [state-machine-alula-spec.md](state-machine-alula-spec.md); the Russian text is normative: on any difference the Russian text is correct.

The name of the notation is **“Alula”** (`Alula`; the owner's word, 2026-10-21: «Alula - ОК»). It is read with the stress on the second syllable (Russian «Алу́ла»); in Russian the word is feminine and is declined like «Луна». Alula is a star in the paw of Ursa Major (a name in the IAU catalogue), from Arabic *al-qafza al-ūlā*, “the first leap” (the stars of “the three leaps of the gazelle”: Alula, Tania, Talitha); a leap is a transition of the machine from state to state. A second, independent meaning is the English *alula*, “a little wing” (Latin *ala*, “wing”, and the diminutive suffix *-ula*): a small group of feathers on the first digit of a bird's wing (the “bastard wing”) with which the bird controls its flight at low speed. A machine file is a “machine table” in Alula. The name's availability was checked on 2026-10-21: no ALULA trademark for languages or development tools was found (ALULA marks in classes 9/42 belong to a few narrow companies: security systems, insurance, oncology; in Russia there are none in classes 9/42, TMview); the `alula-lang` namespaces (GitHub, domains, packages) are free; a manual check of the Rospatent registry is an open item. The former name of the language (versions 2.7–2.13) and why it was dropped are in the history [doc/alula-history.md](../doc/alula-history.md), section 10; the reasons, goals and history of the language are there too.

Format version: 2.22, 2026-10-22. Status: **experimental format; version 2.2 was implemented by an interpreter in another language; equality with the automaton by journal is confirmed on 39 scenarios of one small machine (the chat machine); the expressibility of “Agent step” and “Meeting” was checked by pilots; not implemented: nested machines, `Edits`, the party profile, `Request limit`, `Form returns`, `pass`.** The rules for writing machines are in [state-machine-spec.md](state-machine-spec.md); this file sets the formal notation of the same tables: types, expressions, actions, parties, fragments. The journal is [state-machine-journal.md](state-machine-journal.md); the glossary of English names is [state-machine-glossary.md](state-machine-glossary.md) (the dictionary of automatic JSON names, section 1a). On a difference with the rules of the specification the specification is correct, and this file is corrected after it.

Goal: a machine is described by one file without code in Nova; from the description an executor gives the same behavior as the automaton in Nova: the same transitions, the same structured journal, the same data and queue. Checked by the expressibility of the automata rows (which rows are written without workarounds) and by running one small machine through an interpreter (comparison with the automaton by journal, the header).

The examples are taken from the pilots (excerpts of “Agent step” and “Meeting”); under each one it is said what was changed against the pilot's record. A construct used in an example is defined in sections 2–5, 7–9 or in the catalog (section 12). The labels in parentheses in the text are the numbers of corrections: of earlier versions (А, АМ, E, T, С, ША, ШМ, ШВ, СГ, ИС), of version 2.3 (Н-…), of version 2.4 (И-…), of version 2.5 (Т-…), of version 2.6 (С-1), of version 2.7 (П-1…П-9), of version 2.8 (AL-1…AL-4), of version 2.9 (AL-5…AL-18) of version 2.10 (AL-19…AL-21), of version 2.11 (AL-22), of version 2.12 (AL-23…AL-37), of version 2.13 (AL-38…AL-49), of version 2.14 (AL-50), of version 2.15 (AL-51…AL-55), of version 2.16 (AL-56…AL-62) of version 2.17 (AL-63, AL-64), of version 2.18 (AL-66…AL-75), of version 2.19 (AL-76…AL-81), of version 2.20 (AL-82), of version 2.21 (AL-83…AL-86) and of version 2.22 (AL-87…AL-100, section 0). The examples are excerpts: the section `## Names` (1a) is not shown in them, except the example in section 1a; where a name of an example would get in a Russian machine file a JSON name other than the automatic one, the `## Names` row is named under the example (the samples carry the whole section). The examples of this English version are written in the English form of the language (section 1a): the keywords come from the `en` column of the word table [alula-keywords.tsv](alula-keywords.tsv), and the names invented by an author are English (Latin), so each of them is its own JSON name.

## 1. Machine file

The keywords of this section (section headings, column names, key lines, party kinds) are quoted here in their English form; in the Russian form of a file they are the Russian words, and in the English form they are written by the [word table](alula-keywords.tsv); the rules are in section 1a.

**Extension.** A machine file in Alula is called `*.alula.md` (the machine name is Latin, as in `- machine:`; for example `agent_step.alula.md`); the former names `*.table.md` and `*.table.txt` are not used, there is no transition period (the owner's word, 2026-10-19: “there is no transition period”; version 2.11, AL-22). Parsing does not check the extension: the extension is checked only by the formatting check script (AL-18). A functions file and a fragment file are also `*.alula.md` with a header of their own kind. **A compiled tree** (JSON `machine/2`, section 6) is called `<name>.alula.json` (AL-19): `agent_step.alula.md` ↔ `agent_step.alula.json`; it is not a separate format but the executable form of the language itself — a hand-written tree is also Alula, written in the JSON form; `format: "machine/2"` inside the tree does not change. The former `*.machine.json` is not used, there is no transition period (AL-22). The machine version (`- machine_version:`) is set by the author of the file; a string of the form `alula-<format version>` is recommended (for example `alula-2.22`) — it answers the question “in which language and which version is the machine written”; the caller compares it only for equality with the registry entry (call protocol, section B, item 6).

**Tables** (П-6). The separator row under a table heading (`|---|---|`, `|:---|---:|`) is a row of the signs `-`, `:`, spaces and `|`; parsing skips it. The sign `|` inside a cell is written `\|` (a literal set `"a" \| "b"`, the alternatives of `match`); parsing removes the escaping. In the examples of the format the separator is omitted.

**The comment `//`** (AL-90; as the bare `//` of Nova, D104). In a code block (between ``` fences) and in a heading line `##` or `###` — after the heading text (`## Common events     // parsed before the state rows`) — the sign `//` outside a text literal starts a comment to the end of the line: parsing and the checks do not read it, it does not enter the tree, the generator does not write it (1b). `//` inside a literal is text (`"http://x"`): a comment is looked for after the literals of the line are parsed. A code cell of a table (the code columns: actions, expression, condition, “when”, “response”, “value”, “initial”, “default”, “profile”, “non_decreasing”; the event cell) and a key line (`- Except: …`) have no comment: `//` outside a literal there is a check error; in the prose columns (“note”) `//` is ordinary text, links `https://…` are allowed; an explanation of a table row is the column “note” or a prose paragraph (4.1). The language has no operator `//` (division is `/`, 3.1). The doc comments of Nova `///` and `//!` are not introduced: `///` is an ordinary comment too.

**`## Parameters`: passing values from outside** (П-9). The executor accepts parameter overrides as a “key → value” table: the key is `project.<key>` from the column “project override”; the value is checked against the parameter type (a full map — by the rules of section 2), a key that is not in the column is a load refusal. This is the passing mechanism; where the executor takes the table from (project settings, the scenario `params`, section 11) the format does not define. The keys `project.<key>` are named by the product, they are not part of the language; the column “project override” of the sample stays `—` because the source names no keys. A default value that depends on an external key applies only when the key is present in the override table; otherwise the default value works (AL-11).

**`## Input`.** The input type is a record made of the fields of this section (rule 35, item 1); `initial: input.<field>` takes the value from the input. An optional field (of type `?T`) that is absent from the input equals `none` (AL-48). The invariant is checked by the executor when it accepts a request; a violation is a call refusal (И-1): the executor writes the journal event `input_rejected` and finishes the call with the refusal `NoResult` with the text `input rejected: <reason>`; the machine state does not change. The same refusal — when parsing the input. The event parameters (journal, subsection “Events of the table format”): `reason` — a closed list `json` (the input is not JSON), `missing` (a required input field is absent; an optional one gives no refusal, AL-48), `type` (a field of another type, outside the type bound, outside a literal set, or not an `id` of UUID format, for example `int>=0` at −1), `invariant` (an input invariant is violated); `field` — the input field name (for `missing` and `type`); `index` — the invariant number from zero (for `invariant`). `field` and `index` are optional: with `json` they are absent, and the template skips them. Examples: `input_rejected(reason=json)`, `input_rejected(reason=missing; field=label)`, `input_rejected(reason=type; field=start)`, `input_rejected(reason=invariant; index=0)`. The call request identifier (`call_request_id`) does not lie in the input: the executor gives it (section 9).

**The input of a called machine and `input Type` of the caller** (AL-30). A party `machine <name>(input Type, …)` names a record type whose fields are exactly the fields of the `## Input` of the called machine: the same names and types, the order is not significant; the request fields are the fields of this type, except `profile` (4.2). Therefore an input that the callers pass by fields (`kind`, `session`, `context`, …) is declared by the called machine with the same fields, not with one record field; the record as a whole, if it is needed in the data, is built by `initial` with a record constructor (`AgentRequest { kind: input.kind, … }`, the “Agent step” sample). The field types are compared by the compatibility of section 2: `int` and `int>=n` are compatible both ways (AL-47) — a field `int` in the caller and `int>=0` in the called machine (or the reverse) are one field, the bound is checked by the called machine when it accepts the input (`input_rejected`, `reason=type`). The comparison of the types of the two files is the product's (section 14).

The datum is `int>=0`, initial `0`, `non_decreasing: yes`, `writes: mechanics`; for a field path the initial `0` is set by the datum row with the element record (`attempt: 0` in `lenses`, section 2), and for a path in the “Data” table the `initial` is `—` (Н-5); the attempt number of a request equals the counter value after the increase (mechanics, before sending; at a gate of a human — before the gate is shown, rule 19), the request identifier is `<id>-<number>` (for a set — `<set element>-<number>`). The check of section 10 verifies the datum.
- **A party with free input** (AL-51, AL-52; rule 19) is a party of the kind `human` with `—` in the column `counter` (`—` is the “no value” sign, 1b): it has no gates; a human answers it with a **word of free input** — a party signal without gates: it carries no gate identifier, is accepted by the signal name by a row of the current state and leads a transition (what a word is — below, `signals`); there is no gate record and no counter; the agent gatekeeper does not answer it, therefore `—` is allowed only for the kind `human`. A `human` party with a counter is gates (rule 19). Example: `| interlocutor | human | human(result GateOutcome) | — | message { content str, author str, source str } | — |`.
- `signals` (AL-38) — for the kinds `human`, `enhanced`, the gatekeeper: the **party signals** — what the party says to the machine at a gate: a signal or `signal { field type, … }` — a signal with data (the fields in braces, as at a form of an enumeration, AL-82; the former record `signal(field type)` is an error); the signals are written as in the machine tables (including those of several words: `halt meeting`); the JSON name of a signal and of its fields is built by 1a (AL-53), and where it is wrong it is set by a `## Names` row (AL-60): for `засчитан { находки []Находка }` the glossary gives the signal `counted`, the field `находки` — `findings`, no rows are needed; a signal field is declared in braces through a space, `counted { findings []Finding }`, and in a transition row it is bound as `signal(counted { findings: new_findings })` (3.1, AL-8). The declaration itself names which party may give the signal: these are **all signals of the party**; the signals of a state are the signals of its rows (4.3). A party signal is an event of the party from its declared set (for `human`, `enhanced` and the gatekeeper — a form of `GateOutcome`); it belongs to the open request of that party, and when a human answers — to its open gate and carries its identifier, as rules 15–19 of the specification say (the attempt counter, the acceptance of the response, the words of a human); the gate identifier `<identifier>-<number>` names the party, and the signal is checked against the signals of that party: one it did not declare or one that came from another party is discarded (“a word of a foreign party”, rules 17, 19); a signal of a party with free input carries no gate identifier and is accepted by name in the current state (AL-51, rule 19). It differs from a machine signal (common events, section 9) by being declared at the party and by who may give it. A **word** is the text a human writes to answer; a word carries one of the party signals: at a gate a word is one of the gate words of the party, carries the gate identifier and is accepted once; for a party with free input a word is accepted by the signal name by a row of the current state, there is no gate identifier. For the other kinds — `—`.
- **`parse`** (E1, СГ13) — only for the kind `machine`: a reading primitive (section 7) with a parameter of the type `result`, an optional second parameter — a text literal of the role (`parse_agent_reply("author")`: one host primitive serves several roles) and a result of the given type; for a primitive with the result `by role {…}` (section 7) the given type must coincide with the registry type for that literal (Н-12). The executor calls it when it accepts the response (rule 14), after the “Edits” check (4.2) and before “On accept”, and the **response value** for `response(name)`, `response: Form { … }` and “On accept” becomes the parse result; without `parse` it is the `result` itself. The event `response: Form` requires that the response value be a value of an enumeration. The primitive's hidden reads (`reads`) enter the reads of the state (`Request`, rule 11); the parse is called once per response, the result is stored with the accepted event. A parse by role is the same registry primitive with another role literal (the result `by role` — section 7).
- **A parse failure** (AL-33). A parse either gives a value of the given type or refuses: a response not by form (the artifact is unreadable, there are no excerpts, the comparison did not converge); the remarks of the refusal are a service record that the return of the party reads. A parse refusal is a response not by form (rule 18): no event arises, “On accept” is not executed, the response is not written in `accepted_requests`; while the returns are fewer than “Form returns” (4.2), the executor returns the response to the party (for `machine` — with a new request of the same party with a remark); after exhaustion, and with `Form returns: 0` at once, the request is closed by the event `failure` with the code `FailCode.FormNotFixed` (a code outside the state's list the executor brings to `NoResult`, 4.3). The return and its journal record are executor mechanics (product journal codes — section 5). A value of another type than the one named after `->` (for a result `by role` — not of the role's type) is a host defect, that is a program defect (3.3), not a response not by form.

## 1a. File language and keywords

The Alula language is bilingual (AL-1): a file `*.alula.md` is written either in Russian or in English. The Russian form is the base one; all examples of the Russian specification are written in it. The English form is the same constructs with English keywords; the examples of this English version are written in it. An English sample machine is a separate work and does not affect this section.

**Keywords** are the words that the specification defines: the headings of sections and of the header, key lines, table column headings, state kinds, the words of events and of “To”, the words of expressions, actions, catalog functions, the literals `true`/`false`/`none`, the kinds of word parties, the values of `writes` and `reads`. They are written **entirely in one language — the language of the file**. Mixing is not allowed: a file with Russian headings and the English action `journal(…)` is an error.

**There are two languages, declared by a header line:** `- language: ru` or `- language: en`. The line is optional, `ru` by default. The parsing rules:

- the check does not guess and does not switch silently: the language is taken only from the `language` line or by default;
- a file with an English header (`# Machine:`, `# Functions:`, `# Fragment:`) without `- language: en` is a check error (“the header language is English, and language is not declared”); the same for a Russian header with `- language: en`;
- a keyword not of the file language is a check error with the line number of the first foreign word.

**Free, in any language and mixed** (these are not keywords; mixed — by words, not inside a word, AL-59): the names that an author invents — data, states, functions, types, fields, party signals, fragment parameters and their values; prose comments outside tables (4.1); string values inside data and journal event codes (in Latin by convention, rule 34(б)); the names of host primitives from the registry (as written there); party identifiers (`agent`, `human`, etc.). The header keys (`machine`, `machine_version`, `format`, `functions_version`, `fragment`, `language`) and the primitive classes (`pure`, `reading`, `writing`, `irreversible`) are Latin in both languages.

**JSON.** The `machine/2` tree (section 6) does not depend on the file language: the keywords of both languages correspond to the same keys and values, names enter the tree by their JSON names (below), string values (refusal texts, messages, text literals) — as the author wrote them (AL-10). Therefore files of the two languages with the same JSON names and string values give one tree up to the internal names (below). The sample comparison ([check-alula-samples.py](check-alula-samples.py)) compares the JSON names of declarations (for the Russian sample — automatic and from `## Names`, AL-53, AL-60) and does not compare string values.

**JSON name** (AL-46, AL-53, AL-60) — one rule and one place. A JSON name is the name in the `machine/2` tree, in the journal, in `all_data` and on the wire. It belongs to a name that an author declares and that leaves the machine: a state (the journal field `state`, the parameter `fork`, `text(State)`), a datum (`all_data`, `machine_data`), an input field, a type, a field of a record and of a form, a form of an enumeration with fields, an enumeration element (the wire, `all_data`), a party signal and its field (the wire, a scenario), a primitive (the JSON name is the host registry name), the name of the gatekeeper setting (a project setting key). The JSON name is a row of the section `## Names` (below), and for a name without a row it **is built automatically** (AL-53):

1. a Latin name (`[A-Za-z_][A-Za-z0-9_]*`) — the name itself;
2. otherwise, if the glossary (below) names the whole name, — the English name of the glossary (`число_повторов` → `retry_count`, `ПОВТОР` → `Retry`, `Токены` → `TokenUsage`);
3. otherwise — the transliteration of the name by the table below with the case rule (`оставить правку` → `ostavit_pravku`); each word is transliterated separately, a Latin word stays (`запрос_Agent` → `ZaprosAgent` for a type-like name, AL-59).

**The section `## Names`** (AL-60; Russian `## Имена`) is **the only way** to set a JSON name other than the automatic one. The table `| name | json_name |` (Russian `| имя | JSON-имя |`): the first column is a name declared in this file (in any language, a Latin one included), the second a Latin JSON name `[A-Za-z_][A-Za-z0-9_]*`. A row sets the JSON name of every declaration with this name in the file; if one name is declared in several places and only some need the JSON name, the first column is a **qualified name**: the path of declared names through dots from the top-level namespace — `Type.field`, `Type.Form`, `Type.Form.field`, `Type.Element`, `party.signal`, `party.signal.field`; a row with a qualified name is stronger than a row with a plain one. A name without a row gets the automatic JSON name. The table lists **only** the names whose automatic name is wrong. Check errors (section 10): a row that changes nothing (its JSON name equals the name the declaration gets without it) — “redundant row”; a row for a name or path that is not among the declarations of this file that leave the machine (an internal name, a readable name, a typo) — “name not declared”; a name repeated in the first column; a non-Latin JSON name; equal JSON names in one namespace (below). An automatic name that did not come out Latin (a sign outside the transliteration table) is an error too: such a name needs a row. **There are no parentheses after names in declarations** (`### ОТКРЫТИЕ — операция`, `| расход | ?РасходТранспорта | …`, `тип Утверждение { … }`): there is one way to write it; parentheses `name (X)` of versions 2.9–2.15 are a check error. The section is written by a machine file and a functions file — after `## Types`, by a fragment file — after `## Data` (it has no `## Types`); each file for its own declarations: an included file defines its JSON names itself. No rows — no section. Not written in `## Names`: a field path `name[*].field` (it is made of declared names); keywords and readable names, including the contract data and the data of the “Pause” fragment (`stop_reason`, `to_send`, `open_requests`, `previous`, `call_request_id`) and the binding `reason`, — their JSON name is the `en` word of the word table (AL-49); **internal names** that do not leave the machine — constants, parameters (their external name is `project.<key>`), functions and their parameters, party names (their external name is `id`), event bindings and `let`, lambda parameters, the variable of `for` — enter the tree as written. There are no other ways to set a JSON name.

Example (the “Meeting” sample, Russian form; `Вопрос` is a form of both `ИтогПравки` and `КонтекстРоли`, so the name is qualified; `расход` is from the “Agent step” sample: a plain row sets the name of the datum and of the field of five forms).

**Namespaces** (AL-58). JSON names inside one namespace are distinct; a coincidence is a check error, and one JSON name in different namespaces is allowed. The namespaces: (1) the states of the machine — together with the states of included fragments after substitution (the fragment names enter the state namespace of the machine); (2) the data of the machine (together with the fragment data); (3) the input fields; (4) the top-level types — records and enumerations (with fields and without) together; (5) the fields of one record or one form; (6) the forms of one enumeration with fields; (7) the elements of one enumeration; (8) the signals of one party and, separately, the fields of one signal; the common events of the machine (machine signals) are a separate namespace; (9) the primitives of the machine registry; (10) parameters, constants and the gatekeeper setting names; functions — each name in its own namespace. (11) **The call namespace** (AL-81): catalog functions (section 12), author functions and registry primitives; the name of a function or a primitive (as written, the English name by 1a, for a primitive also the JSON name) does not coincide with a word of a catalog function in either language nor with `range`, and the names in it are distinct: a function does not coincide with a primitive — otherwise a check error; the exception is `новый_ид`/`new_id`: the built-in host primitive stands also in the kind `catalog` of the word table (section 12), so a function or a primitive with this name is not compared with the catalog words (AL-107); data, fields and other names are not in it (3.1). Journal codes (`journal(code)`) and the numbers of common events are not in these namespaces.

**Mixed names** (AL-59). A word of a name — the part between `_` and spaces — is written in the letters of one script: Cyrillic only or Latin only; digits are allowed in any word (`В3`, `v2`). A word that mixes Cyrillic and Latin (`ЗапросAgent`, `ХодV2`) is a check error: such a word has no unambiguous boundary for transliteration and case. Mixing is allowed only between words, through `_` or a space (`запрос_Agent`, `ход_v2`): each word is transliterated separately, a Latin word stays as it is (step 3).

**The glossary for names** (AL-53, AL-61, AL-62) is the methodology glossary of English names [state-machine-glossary.md](state-machine-glossary.md) (version 11). Only its part “Russian name → English name” is normative for names: the rows of the tables of sections 2.1–2.9, 2.11, 2.12 and 2.16 (the first column is the Russian name, the second the English one, both in backquotes) and the records `` `Russian` → `English` `` of section 2.10. The lookup is by the whole name, by an exact match of the string (with case, underscores and spaces). **Caution:** the lookup is by the whole name regardless of the kind of the name, so the automatic name is Latin but may be not the intended one (the type `Утверждение` gives `Approval`, a state `ИТОГ` gives `Totals`, a field `ошибка` gives `failure_error`); for a machine with an English twin the sample comparison finds the difference, otherwise the author checks the name and writes a `## Names` row where needed. Not included: the string literals (2.14), the context exceptions (2.15), the conventions, notes and history; a name to which these tables give two different English names (there is one — `расход`: `usage` and `transport_usage`) has no record: its JSON name is built by transliteration, and the wanted one is written in `## Names`.

**The glossary hash** (AL-62). The normative part of the glossary is pinned by a hash, not by a version number. The text for the hash: the pairs of the normative part in file order (the rows of the tables of sections 2.1–2.9, 2.11, 2.12, 2.16 — by the first two columns; the records of section 2.10 — in their order in the line), each one is a line `Russian → English` (the Russian name, a space, the sign `→`, a space, the English name, without backquotes), the lines are joined by LF (`\n`), there is no LF after the last one, the encoding is UTF-8; the hash is the first 12 signs of the SHA-256 of this text, in lower case. Format 2.22 pins the **glossary hash `60383c370415`** (the same as 2.16–2.21: the glossary did not change). The check ([check-alula-keywords.py](check-alula-keywords.py)) recomputes the hash from the glossary file; another hash is the error “the glossary changed without a format change”: a new or changed pair changes automatic names, and the same machine would give another tree. The format version and the hash change only together; an edit outside the normative part (the literals 2.14, the exceptions 2.15, the columns “Where”, “Source”, “Note”, the conventions, the history) does not change the hash and needs no new format. The version number in the glossary header is for people. An “Alula → JSON” translator needs a copy of the normative part with the same hash.

**Case** of the transliteration (step 3, AL-53). The words of a name are separated by `_` or a space; `_` and spaces at the start, at the end and in a row give no empty words and do not pass into the name (`_ход__агента` → `khod_agenta`). **Type-like names** — a state, a type, a form of an enumeration with fields, an enumeration element — are written together, each word with a capital letter (`PascalCase`): in a word written without lower-case letters (`ХОД`, `В3`) all letters but the first first become lower-case; a capital Cyrillic letter gives Latin with a capital first letter (`Ж` → `Zh`, `Щ` → `Shch`); the first letter of every word is capital: `ХОД_АГЕНТА` → `KhodAgenta`, `ВидВызывающего` → `VidVyzyvayushchego`, `НетОтветаВСрок` → `NetOtvetaVSrok`. **Value-like names** — a datum, an input field, a field of a record and of a form, a party signal and its field, a primitive, the name of the gatekeeper setting — are written in lower case, the words through `_` (`snake_case`): `оставить правку` → `ostavit_pravku`, `находки_В3` → `nakhodki_v3` (if there were no glossary). The rule is taken from the samples and convention 1 of the glossary: types and forms are `PascalCase`, fields, data and functions are `snake_case`.

| Sign | Where |
|---|---|

## 1b. Canonical form (recommended for generators)

A “tree → file” generator (the reverse conversion of the JSON `machine/2` to Alula, AL-21) is bound by one thing (AL-45): the text it writes translates back to a tree equal to the original — the cycle “md → JSON → md → JSON” gives an equal tree. The rules of this section are the **recommended** canonical form of such a text: with it the result is predictable, and two generators write one text; a generator that writes otherwise does not break the requirement if the tree is equal. The reverse conversion loses comment paragraphs, formatting (alignment, line breaks inside declarations) and the names that are not in the tree (the tree holds one JSON name, automatic or from `## Names`, 1a); the meaning is not lost. A file written by a person in another way (the order of key lines, prose, line breaks) stays valid — parsing accepts it.

- **(а) Header.** `# Machine: <Name>` (the Russian form — `# Машина: <Имя>`), where `<Name>` is the Latin name of the machine (`machine` of the tree); an empty line; a list of four items in this order: `- machine: <name>`, `- machine_version: <string>`, `- format: <format version>`, `- language: <ru|en>`; the line `language` is always written, the default is not used. `machine_version` is `version` of the tree; `format` is the format version in which the source was written (the root key `alula_version` of the tree, section 6, AL-108; if it is absent — the format version of the generator).
- **(б) Sections.** The eleven sections of section 1 in order — `## Types`, `## Constants`, `## Parameters`, `## Input`, `## Data`, `## Parties`, `## Functions`, `## Includes`, `## States`, `## Ends`, `## Primitives` — are always written, once each; an empty section is the single line `—` under the heading; the optional section `## Names` (1a) stands after `## Types` and is written only if it has rows; one empty line between sections. The key lines of sections are list items: `- Invariant: <expression>` (one per invariant) — after the `## Input` table; `- Request limit: <expression>` (if `request_limit` is set in the tree) — after the `## Parties` table; `- Result: <Type>` — before the `## Ends` table.
- **(в) States.** The first line of `## States` is `Initial state: NAME` (the Russian form — `Начальное состояние: ИМЯ`), not a list item, then an empty line; states are in the order of `states` of the tree. The key lines of a state are list items, one after another, in this order: `Party`, `Idle term`, `Edits`, `Form returns`, `Request`, `On accept`, `Reads`, `On entry`, `Except` (the Russian ones — `Сторона`, `Срок тишины`, `Правит`, `Возвратов формы`, `Запрос`, `При приёме`, `Читает`, `При входе`, `Кроме`); a key the state does not have or whose value is empty (`—`, `none`) is not written (AL-40); a key with a real default value (`Idle term: 0`, `Form returns: 0`) may be written by the generator. An item with a table (`Request:` of an appeal, `On accept:`) stands before its table, and an empty line stands between a table and the next block; the body of “On entry” of several actions is a nested list, one action per item (4.1).
- **(г) Tables.** The header and the rows have one space on each side of `|`, with no alignment of column widths; the separator row is `|---|` by the number of columns; an empty cell is `—`; `|` inside a cell is `\|`. In the `Request` table an expression equal to the field name is written `—` (AL-56). The actions in a cell are in the order of the tree, joined by `; `; blocks are in braces with a space inside: the branches of a conditional action `if expr then { a; b } else { c }` (AL-70), of a conditional expression `if expr then { expr } else { expr }` (AL-71), the body `for x in xs { a; b }` (AL-72), an action block `{ let l = expr; a }` (AL-73, AL-74); an event pattern is `response: Var { field, field: name }`, a signal with fields is `signal(s { field })` (AL-77); the declaration of a signal with fields in the column “signals” is `s { field type, field type }`, a signal without fields — by name (AL-82). The words of the column headings come from the word table of the file language.
- **(д) Declarations.** Types and functions are written in code blocks under `## Types` and `## Functions` (AL-13), in the order of the tree, **one declaration per line**: `type Name enum A | B` (AL-99), with values — the header `type Name enum` and the lines `| El = "value"` (AL-89, AL-99), `type Name { field type, field type }`, `fn name(parameter type) -> Type =>` and the body of the function on the next line with an indent of two spaces (as one line); a block body: `{` at the end of the header without `=>` (`fn name(parameter type) -> Type {`, AL-84), the bindings `let name = expr;` and the last expression — one per line with an indent of two spaces, `}` — on its own line (AL-75). An enumeration (AL-99, as D406 of Nova): on one line — `type Name enum A | B`, only if all forms are bare names (without values and fields) and the line is not longer than 100 signs; otherwise on several lines — the header line `type Name enum`, then one form per line with an indent of two spaces: `  | El`, `  | El = "value"`, `  | Var { field type, field type }`; the generator writes no empty lines and no comments between forms (parsing allows them, section 2). A `match` alternative on a form with fields is `Var { field, field: name } =>` (AL-82). In a `## Types` block empty lines between declarations are not required and are not written by the generator (parsing allows them; the samples separate groups of declarations by an empty line); between functions — one empty line.
- **(е) Operators.** ASCII only in both languages (AL-42): `->` before a result type; `=>` before the body of a function of one expression (a block body is without `=>`, AL-84), in `match` branches and in lambdas (AL-67…AL-69); `>=`, `<=`, `!=`, `==` in comparisons; `...` in a spread; `..` in a range `a..b` (AL-76), `..=` in an inclusive range `a..=b` (AL-86); `match` branches — through `, ` on one line, by a line break in a multi-line `match` (AL-87): the generator writes `match` on one line when it fits — the line where `match` stands is not longer than 100 characters from its start to its end and no branch has a block `=> { … }`; otherwise multi-line: `{` at the end of the header line, each branch on its own line indented two spaces more than the header line, without a comma at the end, `}` on its own line at the indent of the header line; in a table cell `match` is always one-line; the map literal `[k: v, k: v]`, an empty map is `[]` (AL-85); `in` (Russian `в`, AL-100) with a list literal in `failure(reason in […])`, “when” and `Except` (AL-79); a catalog macro as a list method `xs.filter(x => expr)` (AL-78); `int>=n` (`число>=n`); `yes, <= expr` (`да, <= выр`). The signs are in the word table, the kind `operator` (1a).
- **(ж) Names.** The generator writes every name as it lies in the tree: for a name with a JSON name only the JSON name lies in the tree; internal names lie as written (AL-46); so such a generator writes no section `## Names` (1a) — `### Retry — fork`, `| retry_count | int>=0 | …`; a generator that writes other names (for example the author's preserved Russian names) writes `## Names` for every name whose automatic name is not the JSON name of the tree, and only for them (AL-60); the same state name stands in `Initial state` and in the “To” column. The kinds are the words `appeal`, `operation`, `fork`, `end` (the Russian ones — `обращение`, `операция`, `развилка`, `конец`).
- **(з) File language.** The generator chooses the language by a parameter (`ru` or `en`); all keywords come from [alula-keywords.tsv](alula-keywords.tsv) by this language (1a), with no mixing; the names invented by an author (data, types, fields, functions) and the enumeration values are carried over from the tree as they are.
- **(и) String values and journal codes** are carried over as they are, with no translation or normalization; a string literal is in double quotes, inside are escaped `"` (`\"`), `\` (`\\`), `$` before `{` (`\$`), a line feed, a tab, a carriage return and the null sign (`\n`, `\t`, `\r`, `\0`), other control signs — `\u{HEX}` (a closed list, AL-92). A number — by a decimal record: an integer without `_`, a float — by the record of `text(x)` (3.3; `1e-7`, `1.5e20`, AL-91); the generator does not write `//` comments (AL-90). A call `concat(…)` all of whose arguments are non-empty text literals and calls `text(x)`, with no two literals in a row, is recommended to be written by the generator as an insertion (`concat("turn ", text(n))` is `"turn ${n}"`, AL-80), another call `concat` as a call; `text(x)` as a call; the requirement is one — an equal tree (AL-45).
- **(к) Prose.** Comments and prose are not generated. It is allowed to write `title` of the tree, if there is one, as one paragraph under the header (after the header list); nothing more.
- **(л) The file** ends with exactly one line feed (no empty lines at the end), encoding UTF-8 without BOM, line endings LF.
- **(м) Includes.** A fragment (AL-32): the tree carries it already substituted (section 9) and carries the include node with parameters (section 6); the generator writes the include line of the fragment with all parameters, in one line, the parameters in the order of the table `## Parameters` of the fragment (`Pause(halt_signal: halt, halt_code: "pause_halt", nested: [], request_cancel: stop_transport_turn, reentry: nothing, write_right: "…")`), and does not write the states, data and common events of the fragment as its own: a repetition would be “declared twice” (П-2), and without the include line the parameters of the kind `behavior` (`request_cancel`, `reentry`) would be lost — they are not expressed by substitution into the text, their effect lies on `cancel_open` and `To: previous`. A functions file: the tree carries both the reference (`includes`) and a copy of its types, constants and functions (section 6); the generator writes either the include line (and then does not write the copies) or the copies (and then there is no include line) — otherwise the names are declared twice (section 8); the choice is a generator parameter, by default the include line.

The samples [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md) and [state-machine-agent-step.en.alula.md](state-machine-agent-step.en.alula.md) are written by a person and are not brought to the recommended form: they carry prose (к), the fragment include line with line breaks (м), line breaks inside declarations and multi-line bodies of functions (д); the Russian sample, besides, has Russian names whose JSON names are built automatically, with the section `## Имена` where the automatic name is wrong (ж), and has no `language` line (а). The rest (the header, the order of sections and key lines, tables, operators) corresponds in the samples to the canonical form. The cycle “md → JSON → md → JSON” is checked by the consumer product; the methodology scripts do not check the canonical form (section 14).

**Case** (AL-64): built-in word types and types with arguments are written in lower case (`int`, `str`, `id`, `map`), built-in and author-declared named types — with a capital letter (`State`, `Signal`, `AgentRequest`); fragment parameter kinds (section 9) are not types but a separate group of words; `signal` (a kind — a party signal) and `Signal` (a type — a machine signal) are different words.

**Literal set or enumeration** (Т-1). A literal set — when the set is small, local to one machine, the values are not needed by the journal as enumeration values and do not cross the machine boundary (`turn`, `stop_reason` of “Agent step” — so in the source). An enumeration with values (`type Name enum` and the lines `| El = "value"`) — when the set is common to several machines or fragments, crosses the call boundary (input, response, failure code — `FailCode`), the values are needed for the journal and `text(x)`, or the elements have fields (then it is an enumeration with fields, AL-99). **The values of a set** (AL-25) are any text, including Cyrillic and a space (`"наблюдалось" | "не наблюдалось" | "вывод"` — the words of a role artifact): rule 34(б) allows Latin in the text literals of closed sets but does not require it; the values are written as in the source (the words of the automaton code — in Latin, the words of an artifact — as in the artifact). The restriction `[a-z][a-z0-9_]*` applies only to the values of an enumeration (AL-15, AL-41).

**The type `id`** (Т-2). Text of UUID format: 8-4-4-4-12 hexadecimal signs through hyphens, lowercase (`0192f3a0-7c1e-7b2a-9d4e-5a6b7c8d9e0f`). The check is at data load and at input parsing: a violation of the input is the refusal `input_rejected`, `reason=type`, `field` is the field name (section 1); a violation of data is a load error by the format rules. The format does not fix the UUID version; for the identifiers of sessions, host requests and runs version 7 is preferable (by time, sortable). `id` is assigned to a datum and a parameter of type `str` (the type is forgotten, as with a literal set); the reverse — only a literal of UUID format. `==` is structural, `text(x)` gives the text itself. The value is issued by the host primitive `new_id` (section 7). **Not changed:** the request identifier `<party>-<attempt>` (rule 15, [call protocol](state-machine-call-protocol.md)) and the trace envelope (`trace`, `step`, rule 31) remain as in the specification — `id` serves the data of machines (identifiers of sessions, runs, etc.), not the envelope.

**Enumeration values** (AL-15, AL-41). Values may be given not for all elements; a value is `[a-z][a-z0-9_]*`. An element without a value is shown in `text(x)` and in `all_data` by its JSON name (1a, AL-46): in the file the element name is in the file language, in the tree, in `machine_data` and `all_data` it is the JSON name; the `machine_data` comparison goes by the JSON name (for `FailCode` — by the value, as in the engine).

**The declaration notation is as in Nova** (decision of the owner, 2026-10-19): a declaration is `name type` through a space (a field of a record and of a form, a parameter of a function and of a catalog function, a parameter of a party signature and a signal field, a registry parameter); the result is after `->`, the body of a function is after `=>` or a block `{ … }` (AL-67, AL-84). A colon stands only in a record literal `Type { field: expr }`, in a named argument `name: expr`, in a map literal pair `[k: v]` (AL-85) and in a pattern field binding `field: name` (4.3). The sign `=` in a declaration stands only at the value of an enumeration element `El = "value"` (AL-89), there is none after the type name. **Brackets** (AL-82): the fields of a record, a form and a party signal are in braces (`type Name { field T }`, `Var { field T }`, `counted { findings []Finding }`), and so are an event pattern and a `match` alternative (`Var { field, field: name }`); the parameters of a function, a catalog function, a party signature and a registry entry are in parentheses (`fn name(p T)`, `agent(result Type)`): parentheses after a name are a function, braces are the fields of a record or a form. Tables with a separate column “type” (`## Input`, `## Parameters`, `## Data`) do not change. **Declarations only in a code block** (AL-13): `type` (including an enumeration `type Name enum …`, AL-99) and `fn` are written inside a code block (``` fences) under `## Types` and `## Functions`; a declaration line outside a code block is a comment (a paragraph) and a check warning: markdown would distort `|`, `{}`, `->`.

**A style rule: the name of a field does not coincide with the name of its type** (AL-54; a recommendation, not a check error). The rule covers the fields of records and forms and the machine data (the “Data” table). A field names the role of the value in the record, a type — the kind of the value: `tokens Tokens`, `check Check` (in the Russian form before 2.22 `текст текст`) read as a repeat and do not say what the field is for; better `reply str`, `token_usage Tokens`. A coincidence is the equality of the field name and the name of its type ignoring case, after removing `?` and `[]` (`check ?Check` is a coincidence). The field names of the samples (“Agent step”, “Meeting”) are not changed: they are names of the tree and code of the consumer product, a renaming would break them. A check warning — later (section 14).

**Type records and Nova** (checked against the language specification and the automata code): as in Nova — `[]T`, the tuple `(T1, T2)` (in a type position), `map[K, V]` (in Nova `HashMap[K, V]`; the literal `[k: v]` as in Nova, AL-85), the record `type Name { field T }`, the enumeration `type Name enum A | B`, with values and fields at the forms — on several lines with `|` (as `type Name enum …` of Nova, D406; AL-89, AL-99; in Nova a value is an integer `El = 0`); the translation of names — `int`, `str`, `f64`, `bool` (as in Nova; since 2.22, AL-94; before — `text`, `float`). **Extensions of the format** that Nova does not have: `?T` (in Nova `Option[T]`), `int>=n`, the literal set `"a" | "b"`, `id`, `full map[K, V]`; the other differences are in the list of section 14.

**Data.** The table `| name | type | initial | non_decreasing | writes |`.

- `name` is a datum or a **field path** inside a map: `name[*].field` (`*` is any key; for a nested one `name[*].field.field`). A row with a path carries only `non_decreasing` and `writes` and acts on every value of the map; `type` is the field type, `initial` is `—` (the value is set by the row of the datum itself) (С11).
- `initial` is an expression or `input.<field>`.
- `non_decreasing` is `—`, `yes` or `yes, <= expr`; the expression may be any expression over constants, parameters and the input (`max(1, limit)`); the bound is checked by the executor after the transition (for a path — at the write; a violation is a machine error). If the bound in the primary source is wrong for some values, it is not written.
- `writes` — who changes the datum: `rows` (everything written in the machine tables: the row actions, the “On accept” block, writing primitives called from the tables; the default), `mechanics` (executor writes outside the machine text: attempt counters, the transfer from `to_send`, `open_requests`, rules 14, 15, 21), `rows_and_mechanics` (both; the exception of rule 29 is named explicitly), `fragment` (data of an included fragment), `rows_and_fragment` (the machine rows and the fragment rows: the datum `stop_reason`) (А3, E5). `writes` is set for the whole datum; a path has its own value: a write from a transition row into a field with `writes: mechanics` is a table check error (С11).
- **Contract data** is entered into the table and enters `all_data` (АМ8): `open_requests` (`[]str`, initial `[]`, `writes: mechanics`) is entered by the “Pause” fragment — it is read by `pass` and `cancel_open` (section 9); for a machine without the fragment that reads it itself, the machine enters it; a declaration in two places is a name conflict (rule 36), a check error (ША1, ШВ3); `to_send` (`[]str`) is `rows_and_mechanics`: the rows write it (Lock, LensRefusal), the mechanics moves the parties to `open_requests` (rule 21, СГ5); the party attempt counter is the datum from the column `counter` of “Parties” (section 1, СГ1).
- **The composition of `all_data`** (СГ2, ША1, Н-1): **every** datum named in the `## Data` tables of the machine and of the included fragments, and the contract data (the previous item); a field path is inside its datum. The sign is one and is checked by the tables: named in a table — included; there are no exceptions among the named. Therefore data that the source relates to external objects and the assignment are also included (for “Meeting” `proposal`, `copy`, `copy_fingerprint`, `witness_answers`, `lens_findings`, `summary`, `archive`, `author_question`, `lens_order`), and the copy of the input (`agent_request` of “Agent step”): the primary source gives for ERROR “all variables and stores”, rule 11 of the specification — “all data of the machine”. Only what is not in the tables is not included: executor data and the envelope (`state`, `trace`, `step`, `event_counter`, `cause`, `accepted_requests`, the journal) and the stores of rule 31 (`human_words`, `failure_texts`; a human's word and a failure text are not written to the journal in full). Encoding — section 5.

## 3. Expressions

The words of expressions (`if`, `then`, `else`, `and`, `or`, `not`, `let`, `match`, `true`, `false`, `none`, `unreachable`) and the readable names are quoted in the English form; the Russian form is in the [word table](alula-keywords.tsv), the kinds `expr` and `readable` (1a).

### 3.1 Grammar

```
expr := literal | true | false | none | unreachable | name | ( expr ) | expr.field | expr.N | expr[expr]
     | Type { field: expr, ... } | Type.Form { field: expr, ... } | Type.Form     record, form with fields, form without fields
     | { ...expr, field: expr, ... }                        copy of a record with fields replaced
     | (expr, expr, ...)                                  tuple (from two fields)
     | [expr, ...] | [expr: expr, ...]                       list; map (the key is an expression, AL-85); [] is an empty list or map by the expected type
     | not expr | -expr | expr (+|-|*|/|%) expr | expr (==|!=|<|<=|>|>=) expr
     | expr (and|or) expr | expr ?? expr
     | expr..expr                                       a range: half-open [a, b) (AL-76)
     | expr..=expr                                      an inclusive range [a, b]: a..(b + 1) (AL-86)
     | if expr then { expr } else { expr }
     | { [let name = expr;]... expr }                     block expression: bindings and the last expression (the value of the block)
     | match expr { alt [| alt]... [if expr] => expr, ... , else => expr }       exhaustive; on one line branches through `,`, multi-line — each branch on its own line without `,` (AL-87)
     | name(expr, ...[, name: expr, ...])                     catalog function or author function (pure); named arguments come after positional ones
     | expr.macro(name => expr) | expr.fold(expr, (name, name) => expr) | expr.dict(name => expr, name => expr)     a catalog macro is a list method (AL-78)
     | call(primitive, expr, ...)                      reading: only in “Request”, “profile” and in “let” of “On entry”/“On accept”; in any position of these expressions (section 7)
alt := Type.Value | Value | Form | Form { field, field: name, ... } | Type.Form { field, field: name, ... } | literal     Value is a bare element name, looked up among the declared enumerations (AL-88, AL-104)
```

- **Precedence** (highest first): parentheses `( )`, `.`, `[]`, call; unary `-`; `* / %`; `+ -`; comparisons; `not`; `and`; `or`; `??`; `..` and `..=` are the lowest, as in Nova (AL-76, AL-86): `a..b + 1` is `a..(b + 1)`, `0..n ?? 0` is `0..(n ?? 0)`, `a..b == c` is `a..(b == c)` (so a comparison with a range is written in parentheses); `..` and `..=` are not chained: `a..b..c`, `a..=b..c` are errors. `match` captures everything to the right; the branches of `if` and a block expression are blocks, their boundary is the closing `}` (AL-71, AL-75).
- **Literals:** integer `12`, float `0.0`, text `"…"` (with insertions `"…${expr}…"`, below); `true`, `false`; `none` — the absence of a value of `?T`. **Numbers** (AL-91; D44 of Nova, `decimal-int` and `float`): an integer is `[0-9] (_? [0-9])*` (`12`, `1_000`: the sign `_` only between two digits); a float is an integer, `.` and an integer (`0.5`, `1_000.25`) with an optional exponent, or an integer with an exponent; an exponent is `e` or `E`, an optional sign `+`/`-` and an integer (`1.5e-3`, `1e-7`, `2E5`, `1.5e+3`); hexadecimal, binary, octal literals and type suffixes are not introduced (as Nova rejected suffixes). **The lexing order of a number** (as the Nova lexer `novac/src/lex/lex.nv`): the digits of the integer part with `_` between digits; a dot enters the number only if a digit follows it right away — therefore `1..n` is `1`, `..`, `n`, `0..3` is `0`, `..`, `3`, `1_000..2_000` is `1_000`, `..`, `2_000`, and `1.` without a digit after the dot and `1..` are not a float; then an exponent, if a digit stands after `e`/`E` (and a sign) — `1e3` and `1.5e3` are one float number; no letter, digit or `_` of a name touches a number: `1__0`, `1_`, `1_e5`, `1.5_`, `1e`, `1e+`, `0x1F` are errors; `_1` is a name, not a number. **Escapes** in a text literal (AL-92; a closed list, as D467 §2 of Nova): `\"` — a quote, `\\` — a backslash, `\$` — the sign `$` (`\${` is `\$` and `{`: no insertion, AL-80), `\n`, `\t`, `\r` — a line feed, a tab, a carriage return, `\0` — the null sign, `\u{HEX}` — a Unicode sign by one to six hexadecimal digits (the surrogates `D800`…`DFFF` and values above `10FFFF` are an error); any other sign after `\` is a check error; `\xNN` of Nova is not taken (covered by `\u{…}`), there is no line continuation `\` + a line break — a literal stands in one line; in a table cell `\|` is the escaping of the cell (П-6), parsing removes it before parsing the literal. The word “no” (Russian `нет`) is not a literal (rule 30: the “no” of the specification is `none` of `?T`). `unreachable` is an expression of any type: a program defect, the evaluation is stopped by the executor, like `require(none)` (3.3, И-3); it stands in the `match` branch for a form that by the contract does not arrive (E1).
- **Names.** A name is a datum, a constant, a parameter, a function, a binding. A state reads any name from its reads (`Reads`; for an appeal — the `Request` table), whatever its `reads` is (T9). An event field binding, `let` and a lambda parameter are visible only in their scope; an event field binding does not coincide with the name of a machine datum (4.3, AL-26). A callable and a value lie in different namespaces: an author function occupies the call namespace together with the catalog functions and the primitives (1a, namespace 11), while data, constants, parameters and bindings are the value namespace; therefore a bound field `text` and a call `text(x)` do not interfere, and an author function coincides neither with a catalog function nor with a primitive (AL-81). **Reserved words** (СГ12) are never the name of a binding, a datum or a field: `in`, `then`, `else`, `and`, `or`, `not`, `let`, `match`, `if`, `for`, `true`, `false`, `none`, `unreachable`.
- **Field binding with a colon** (AL-8). A field of a signal or a form is declared in the Nova notation through a space (`findings []Finding`, section 2); a binding in a pattern of a transition row is `field: name`, the colon is read “field → name” (`signal(counted { findings: new_findings })`, `response: Finished { text, artifact, usage: received }`, the alternative `Finished { text, usage: u } => …`); if the name coincides with the field, the single name is written.
- **A lambda** is unary (binary only in `fold`); a parameter that is not needed is written `_`; lambdas stand only in a macro argument. The record is `name => expr`, a binary lambda has its parameters in parentheses: `(m, _) => m * 2` (AL-69); the body expression may be a block expression: `x => { let y = x * 2; y + 1 }` — as in a `match` branch and unlike the body of a function, where `=> {` is an error (AL-84; a decision of the methodology for 2.21, confirmed by the owner (methodology chat, 2026-10-22: «по рекомендации»)); the sign `=>` is the same as in a `match` branch and the body of a function of one expression (as in Nova), and `->` stands only before a result type. Nova's record `|m, _| m * 2` is not taken: GitHub splits a table row at every sign `|`, even inside backquotes, and a lambda in a cell (`initial` of the data, actions) would need `\|`; besides, `|` already separates the values of a literal set and the alternatives of `match`.
- **Readable names of the executor** (not computations, rule 11): `input`; `event.id` (of any event); `event.<field>` (a field of the event data of a row or a chain, rule 13); `party` (for a set — the identifier of the event's party; in the “profile” and “Request” of a set — the current party); `reason` — the failure code of the event `failure(reason)` (4.3; visible to the row and the chain, AL-49); `state` (section 9; type `State`); `transition_note` (type `JournalEvent`; in “On entry” and in the “response” of ends; defined when the machine has entered ERROR, and ERROR is entered in two ways: by `machine_error` — the record of this action (А4) and by an executor machine error (3.3) — the record `machine_error`; both ways give a record, ША8, СГ6); `all_data` (a record of the machine data; the composition is in section 2; in the action `journal(all_data)` the same name is an abbreviation of the event `machine_data`, section 5, И-2). `previous` and `call_request_id` are not executor names but data of the “Pause” fragment (section 9, T6). The JSON name of a readable name is the `en` word of the word table, the kind `readable` (`party`, `reason`; 1a, AL-49). The names `trace` and `step` (the envelope, rule 31) are available **only** in the “Request” expressions of a party of kind `machine` — this is the envelope of a nested machine call (rule 35, item 1); in conditions and actions the envelope is not read.
- **Macro methods** (AL-78). The eight catalog macros (`filter`, `map`, `any`, `all`, `count`, `first_where`, `fold`, `dict`, section 12) are called as a method of their first argument — a list: `xs.filter(x => expr)`, `xs.fold(initial, (m, x) => expr)`, `xs.dict(x => key, x => value)`; a chain is `xs.filter(…).count(…)`. The other catalog functions, author functions and primitives are called by a call `name(…)`. A name after a dot without `(` is a record field (`result.probes`), a macro name after a dot with `(` is a method call; a record or form field named as a macro is a check warning, not an error (AL-106): the fields of the packages' machines have such a name (`count`), and the parentheses tell the method call `x.count(…)` from the field `x.count`. The former call of a macro as a function with the list as the first argument (`filter(xs, x => expr)`) is an error. The tree is the former macro call, the receiver being the first argument (section 6).
- **A range** (AL-76). `a..b` is a list of integers `[a, b)`: half-open, empty when `b <= a` (as the former `range(a, b)` and Nova's `a..b`; the inclusive one is `a..=b`, below); the operands are `int`. **Lexing:** `..` after a number or a name is always the range sign, never a part of a fractional literal: `1..n` is read `1`, `..`, `n`, and `0.5..2` is `0.5`, `..`, `2` (the type is an error: the operands are not `int`); `...` is the spread (the longest match). A method on a range is written in parentheses: `(1..n).fold(…)` (`.` binds tighter than `..`). In the tree — a call `range` (section 6).
- **An inclusive range** (AL-86). `a..=b` is sugar for `a..(b + 1)`, as Nova's `a..=b` (the end `b + 1`): a list of integers from `a` to `b` inclusive, empty when `b < a`; the operands are `int`; the precedence and the rules are those of `..` (the lowest, `a..=b + 1` is `a..=(b + 1)`, not chained, a method in parentheses: `(1..=n).fold(…)`). **Lexing:** the longest match — `...` (spread), then `..=`, then `..`; `..=` is written without spaces: `a.. =b` (`..`, then `=`) and `a..==b` are errors. In the tree — a call `range` with the arguments `a` and `b + 1` (section 6), the same as for `a..b + 1`.
- **A map literal** (AL-85). `[key: value, …]`, as Nova's `[k: v]` (`[ActionKind.Read: "ask", ActionKind.Write: "deny"]`, `["a": 1]`): after `[` the first expression is parsed; the next sign `:` means a map literal, then pairs `expr: expr` through commas; `,` or `]` means a list literal; the pair separator is the first `:` outside nested `()`, `[]`, `{}` (`[f(x, name: 1)]` is a list: the `:` of a named argument stands inside the parentheses). `[]` is an empty list or an empty map by the **expected type**; the sources of the expected type (the list clarified after 2.22, AL-105): the type of a datum (the column “type”), a constant, a parameter; the type of a field — in a record or form literal, in a record copy and in the cell “expression” of the `Request` (the type of the input field of the called machine, otherwise of the datum of the same name); the result type of a function from its header (the body is `[]`); the type of a parameter of a function with a declared signature — an author function (an argument of a call); the type of the left side of an assignment; the type of the other operand of `==`, `!=`, `+` (`to_send != []`, `open_requests == []`); for the right operand of `??` — the type of the place, and without it the type of the left operand without `?` (`m[k] ?? []`); the value of an `if`/`match` branch and the last expression of a block — the type expected by the place; the initial value of `fold` — the result type of the call; the kind of a fragment include parameter (`nested: []` — an empty list of machines, section 9). The type of a call `xs.filter(…)`, `remove(xs, x)` and `without_key(m, k)` is the type of the first argument: by it the type of the other operand is known (`xs.filter(x => x > 0) == []`). A parameter of a catalog function by the signature of section 12 is not a source of the expected type; where there is no expected type (for example, `[] == []`), `[]` is a type check error. Keys and values are expressions evaluated left to right (3.3); a repeated key in a literal is a check error, the literal of a full map names all keys (section 2). There is no map literal in braces: `{expr: expr}` and `{}` are errors (in 2.20 and earlier — a map; there is no transition period).
- **The set after `in`** (AL-79; Russian `в`, AL-100) is a list literal: `reason in [FailCode.A, FailCode.B]`, `stop_reason in [""]`; it stands only in `failure(reason in […])`, “when” of ends and `Except` (4.3, 4.7); the elements are values of a closed type (enumeration elements, literals without insertions); `in {…}` is an error.
- **Insertions in text literals** (AL-80). `"…${expr}…"` — as in Nova (`"${file}:${line}"`, `"turn ${number} of ${limit}"`; the Russian form is the same). (a) Inside `${ … }` — any expression of a type for which `text(x)` is defined (int, f64, str, a literal set, `id`, an enumeration, `State` and `?A` of them, section 12); `bool` and composite types are a check error; the value is inserted as `text(x)` (3.3). (b) A literal with an insertion is a value of the type `str` (3.2), not a literal of a literal set: a set `"a" | "b"` (section 2) and `in […]` (Russian `в […]`) hold only literals without insertions. (c) The sign `${` in text is written `\${` (escaping with `\`, as for `"` and `\`, 1b); a single `$` needs no escaping; an empty insertion `${}` and an unclosed one are an error; literals, including ones with their own insertions, are allowed inside an insertion, the depth is not limited (`"${if has(x) then { "has ${require(x)}" } else { "none" }}"`); in a table cell the sign `|` inside an insertion, as everywhere in a cell, is written `\|` (П-6) — an expression with `|` is better moved into a `let`. (d) The tree schema does not change: the parse unfolds a literal with insertions into a call of the catalog function `concat` (section 12; Russian `склеить`) by one rule: the parts of a literal are the text fragments and the insertions in order, empty fragments are dropped; a literal without insertions is the literal itself; a single insertion part (`"${x}"`) is `text(x)`; otherwise it is a call `concat(…)` with the parts in order, at least two arguments, an insertion being `text(x)`: `"${file}:${line}"` is `concat(text(file), ":", text(line))`, `"a${x}"` is `concat("a", text(x))` (section 6); the generator writes as an insertion only a call `concat` of the canonical form (1b, a recommendation). The sign `+` of text stays (3.2).
- **An alternative of a form with fields** (AL-82). A `match` alternative on a form with fields is a pattern, as in the event cell (4.3) and in Nova: `match result { Finished { text, usage: u } if has(text) => …, Truncated { usage } | Cancelled { usage } => …, else => … }`; the fields are bound as names (`field: name` — with renaming, a single name — the same field), the bindings are visible in the guard and in the branch; a form without fields is a name without brackets. The form name is looked up in the type of the expression after `match` (as `response: Form` — in the type `result` of the party); the qualified record `Type.Form { field, field: name }` is allowed, as `response: Type.Var { … }` (4.3), and its `Type` is the type of the `match` expression, otherwise it is a type check error (`match result { TurnResult.Finished { text } => text, else => "" }`); `Name { … }` in an alternative is always a pattern, not a literal: the alternative stands before `=>`, and a value of a form with fields in an expression is written only with the type name `Type.Var { field: expr }`, therefore `Name { … }` without a dot in an expression is a record literal of the type `Name`. Alternatives joined by `|` have their own braces each. The former record `Form(field, field: name) =>` is an error; parentheses after a name are only a function call.
- **`match` branches** (AL-87, by D452 of Nova: `match` arms on one line are separated by `,`, in the multi-line form only by a line break): on one line branches are separated by `,` — `match kind { Delete | Move => true, else => false }`; there is no comma after the last branch. A multi-line `match` (in a code block) separates branches by a line break: `{` stands at the end of the header line, each branch is on its own line, without `,` and `;` at the end, `}` is on its own line; a branch `=> { … }` may take several lines (line breaks inside a branch block do not split branches), the branch `else => …` the same. Branches are alternatives, not a sequence, therefore `;` between them is an error; `,` at the end of a branch line of a multi-line `match` is an error (D452 removed the comma in the multi-line form, the trailing one included); two branches on one line of a multi-line `match` and a branch on the line of `{` or `}` are errors (there is no mixed form). A table cell is one line, therefore `match` in a cell is always one-line. `;` inside a branch block (`=> { let x = expr; x }`) is the separator of the block and stays.
- **Bare names** (AL-88, AL-104; as rule 1 of D478 of Nova). The name of an enumeration element or of a form without fields is written without the type name: in a `match` alternative, in an element of `in […]`, in a key of a map literal and a full map literal and the index `expr[key]`, on a side of `==`, `!=` and in other places of an expression. A bare name is looked up among the enumerations declared in the machine, in the included functions files and in the fragments; the expected type of the place is not needed for the lookup; the type of a bare name is the type that declares it, the format 2.22 does not introduce a general check of operand types (section 14). A check error (the qualification `Type.El` is needed): the name is declared in two types; the name coincides with a datum, a constant, a parameter or a binding. The qualified form `Type.El` is always allowed. The choice between sums by the expected type (D478 of Nova) is not taken: the translator does not infer the type of every place. State names — the literals of the built-in enumeration `State` — were written so before too (`state != Pause`, section 9). A form with fields in an expression is only `Type.Var { field: expr }`: `Name { … }` without a dot is a record literal of the type `Name` (below, AL-82). Example (the same meaning as the qualified record): `match kind { Delete | Move | Execute => true, else => false }`, `failure(reason in [ConnectionLost, Timeout, NoResult])`, `check == Valid`, `PERMISSION_POLICY[Read]` (a key of the type `ActionKind`); if `Valid` is declared both in `Check` and in another enumeration of the machine, one writes `check == Check.Valid`.
- **Not introduced from the methodology's count:** `contains`, slices, postfix `?`, sorting, loops and recursion outside `for`.

**The position of a block** (AL-74, AL-75). There is one block sign — `{ … }`; what it holds and whether it has a value is given by the position:

| Position | Where | Block content | Value |
|---|---|---|---|
| action | a row “Actions”, “On accept”, “On entry” of an operation and an end (4.5, 4.7), a branch of a conditional action, the body of `for`, a block `{ actions }`; not “On entry” of a fork (only `let` bindings there, 4.6) | actions joined by `;`, including `let name = expr` (visible up to `}`) | none |
| expression | a branch of a conditional expression, a block body of a function (after the result type, without `=>`, AL-84), the right side of an assignment and of `let`, an argument, an expression cell | zero or more `let name = expr;`, lastly one expression | the last expression |

A block expression differs from the literals with braces so: a record and form literal stands after a type name (`Type { … }`), the pattern of a `match` alternative — after a form name, before `=>` (AL-82); a record copy starts with `...`; otherwise `{` opens a block. There is no map literal in braces — a map is written `[k: v]` (AL-85), so no look-ahead to `:` is needed; `{}` is an error: there is no empty block, an empty map is `[]`. After the result type in a function header `{` always opens a block body, and right after `=>` there is never a block (AL-84).

Example of expressions (the “Agent step” pilot, functions).

```
fn needs_elevated_attention(action_kind ActionKind) -> bool =>
  match action_kind {
    ActionKind.Delete | ActionKind.Move | ActionKind.Execute | ActionKind.Network | ActionKind.SwitchMode => true
    else => false
  }

fn retry_pause(n int>=0) -> int =>
  (1..n).fold(RETRY_PAUSE, (m, _) => m * 2)

### 3.2 Expression types

| Rule | Record |
|---|---|
| Raising `T` to `?T` | in an assignment to a field `?T`, in a record constructor field, in a function argument with a parameter `?T`, in a branch of `if`/`match`, to the right of `??` |
| `if`, `match` | branches `T` and `?T` (or `none`) give `?T`; branches of one type — that type |
| `??` | `?T ?? T` is `T`; `?T ?? ?T` is `?T`: the right operand of either of the two types, the result is `T` only with the right `T` |
| `+` | int, float (cannot be mixed), text (concatenation), a list of one type (concatenation: the left first) |
| `==`, `!=` | structural for records, tuples, lists, maps, enumerations, including those with fields (a form without fields — `x == Type.Var` or a bare `x == Var`, AL-88; a form with fields — `x == Type.Var { field: expr }`), literal sets, `?T`; `T` with `?T` — through raising (`none` is not equal to a value) |
| `<`, `<=`, `>`, `>=` | int, float |
| `expr[key]` | map: `?V`, an absent key is `none` (not an error); for a full map — `V`. List: `?T`, an index out of bounds is `none` |
| Literal set | the value of the expression is a **set of values**: a literal is one; `+` — pairwise concatenations; `if`/`match` — the union of the branches; `require(x)` — the set of `x` without `none`; `non_empty(x)` — the set of `x` without `""`; `text(x)` for an enumeration or its subset — their values; assignment and comparison with a datum of the “literal set” type check the inclusion of the set. ### 3.3 Evaluation

- Evaluation is strict, left to right: function arguments, record fields, list and map elements — in the order of writing; `match` branches — top to bottom, the `if` guard — after the alternative matches; a `let` binding in a block — first the value, then the rest of the block. **Lazy** are only `if`, `and`, `or`, `??`: an unselected branch and a right part that is not needed are not evaluated.
- **A reading call inside `if`/`match`** (E4): the selected branch evaluates the call, the unselected one does not (laziness above); the read of the call enters the reads of the state unconditionally, by the `reads` list of the primitive. Calls in arguments are evaluated in the order of writing.
- **The language is not total.** Two kinds of partial operations (ША8, СГ6, ШВ1, СВ2).
  - **A program defect** (И-3): `require(x)` with an empty `x`, `non_empty("")` and `unreachable` — the process is stopped by the executor (not the table); there is no transition to ERROR, the machine state is not rolled back; the call response is an end with `NoResult`; the journal of the defect is at the executor's discretion (this is how `required` of the automata behaves).
  - **A machine error:** `int` overflow, division by zero, going outside `int>=n`, `int(x)` out of range, a repeated key in `xs.dict(…)`, an absent key in `name[key].field = expr`, an index out of bounds when writing into a list. The executor writes the journal event `machine_error` with the parameter `reason` — a word from the closed list `overflow`, `division_by_zero`, `bound_violation`, `conversion_range`, `duplicate_key`, `missing_key`, `list_index` (journal, subsection “Events of the table format”) — and enters ERROR; this event is the `transition_note` (3.1).
  - Indexing a map and a list when reading is not a partial operation.
- `if` is not nested into a branch of another `if` (three or more outcomes — a `match` with guards or a fork).
- `text(x)`: an integer is a decimal record; a float is the shortest decimal record that is reversible to the same float; an integral value is written with `.0` (`1.0`, `0.0`); without an exponent `e` if `1e-4 <= |x| < 1e16`, otherwise an exponent of the form `1e-7`, `1.5e20` (lowercase `e`, without `+` and without leading zeros of the exponent); examples: `0.0`, `2.0`, `0.42`, `0.0001`, `1e-7`, `1.5e20` — each record is also a float literal (3.1, AL-91), therefore the generator writes the value back with it; NaN and infinity are a machine error (А1); an enumeration is the value of the element (for an element without a value — the JSON name); `State` is the JSON name; text is itself; `none` of any of these types is `none`. For `bool` and composite types `text` is not defined.

## 4. States

### 4.1 General

The heading `### NAME — kind`: kind is `appeal`, `operation`, `fork`, `end`; **the JSON name of the state** (1a, AL-46, AL-53, AL-60) is Latin, for the journal and the envelope (the field `state`, the parameter `fork`, `text(State)`): automatic (Russian `ПОВТОР` → `Retry` by the glossary; for a Latin one the name itself, `### Retry — fork`) or, where it is wrong, a `## Names` row (Russian `| ОТКРЫТИЕ | Opening |`, `| Pass | Gate3 |`); there are no parentheses in the heading. The `№` of a row = the label `// NAME #n` in the primary source. The **first** suitable row is selected. The initial state is the first line of the section `## States`: `Initial state: NAME` (А8); the check 34(г) requires that it name a state of the section. **The reads of a state** (rule 11, AL-39): for an appeal — the table `Request:` (4.2), for an operation, a fork and an end — the key line `Reads:` with the names of data that are read by the “On entry”, the conditions and the actions of the state, through commas; a state that reads nothing writes no `Reads:` line, an appeal without request fields — no `Request:` line (AL-40); the reads of a reading primitive (section 7) enter the reads of the state by its `reads` list; the `Reads` of ERROR is `all_data` (all data of the machine without executor data; the names are read as data). In the examples of this English version the state names are the Latin names, so they are their own JSON names (AL-46, AL-53).

**State key lines** (С-1) — `Party`, `Idle term`, `Edits`, `Form returns`, `Request`, `Reads`, `On entry`, `On accept`, `Except`, and in the sections `## Parties` and `## Ends` — `Request limit` and `Result` — are **items of a bulleted list**: `- Party: agent`, `- Idle term: IDLE_TERM`, `- Reads: retry_count, turn`. The marker `- ` is optional in parsing (compatibility with version 2.5), required in writing; the reason: markdown glues consecutive lines into one paragraph, and the preview shows “Party: agent Idle term: IDLE_TERM Request:” as one line. **Empty values are not written** (AL-40): a key with an empty value (`—`, `none`: no request fields, nothing to read, no term, no work on entry) is skipped, and an omitted key means the default; `- Idle term: —`, `- On entry: —`, `- Input: none` are not written. A key with a real default value (`- Idle term: 0`, `- Form returns: 0`) may stay written: so it shows that the value is chosen, not forgotten. The other rules of writing:

- a table (request field | expression | reads of `Request`; event | actions of `On accept`; the state rows) stands **at the block level**, not inside a list item: between the last list item and the table, as between two tables, there is an empty line; the item itself (`- Request:`, `- On accept:`) remains the last in the list before its table;
- a value in one line is in the item itself (`- On entry: let moment = call(time_now)`); the body of “On entry” of several actions is a nested list, one action per item (`  - let current_time = call(time_now);`), the sign `;` at the end of the item is kept, parsing glues the items into the same action list through `;`;
- the state heading `### NAME — kind` and the line `Initial state: NAME` (one per section) are not written as a list.

**Prose** (П-1, AL-12). A paragraph — one or several lines of text between empty lines (an empty line is needed both before and after) outside tables, outside code blocks and outside key lines — is a comment for the reader: translators and checks skip it, the signs “`” and “« »” inside it are allowed. A text line pressed against a table, a heading or a list item without an empty line is not a paragraph (markdown glues it to the neighboring block): the formatting check warns, parsing reads it as an extra line of the neighboring block. Headings `#`, `##`, `###`, tables and the list items of key lines (`- Key: …`) are not prose. So that a typo in a key does not become a silent comment, the formatting check (section 10) warns about a paragraph line that begins with a word from the list of keys (`Party`, `Idle term`, `Request`, `Reads`, `Edits`, `Form returns`, `On entry`, `On accept`, `Result`, `Except`, `Request limit`) without the marker `- ` or with a typo in it.

**“To”:** a state name; `previous`; `preparation_return` (rule 24); `same` (stay in the state; allowed in the rows of an appeal and in common events; without a rerun only the actions of the row run — no re-entry, no request is sent; with a rerun — `same, rerun` — the state is entered anew: the open request of the appeal is cancelled and a new one is sent; example: `| 3 | signal(retry) | — | log(retry_requested) | same, rerun |`); the suffix `, rerun` (rule 18); `—` for a row with `machine_error`.

**The fork default and `else`** (AL-57). The `else` row by rule 27 is written last, with the action `machine_error("fork_no_match", fork: "<JSON_name>")` (the value of `fork` is a text literal, АМ6, T10) and `To` `—`; its label is the next number after the last condition row. The `else` row **is required** unless the exhaustion of the conditions is proven by a type; a fork without `else` and without proven exhaustion is a check error. **The exhaustion is proven by a type** when the condition of every row except `else` is a comparison of one and the same name `x` (a datum, a `let` binding, `event.<field>`) of a closed type with one of its values: `x == Type.El` for an enumeration `Type` (or a bare `x == El`, AL-88), `x == Type.Var` for an enumeration whose forms all have no fields, `x == "label"` for a literal set (`"a" | "b"`, section 2) — and the rows name all values of the type (as for `match`, section 2). Then `else` is optional: a fork without it cannot be left without a suitable row; a written `else` is unreachable — a check **warning**, not an error (usually it is an `else` with `machine_error` left by habit). No exhaustion is proven by a condition over text — a name of the type `str` (`continuation == "…"` with string labels: however many labels there are, the type does not close them; to close the set, declare the type as a literal set or an enumeration), over two fields (a pair of enumerations: a product of types is not proven, `else` is a trap for an unforeseen combination), over `?T` (`none` is not named), a condition with `and`, `not`, `!=`, `<`; such forks keep `else`.

- **Request.** `reads: party` — a request field to the party; `executor` — a name that the state rows read, and it does not go into the request: the entry **declares a dependency** of the state (it uses this datum in its conditions and actions; rule 11 “a step reads only its Input”), not an action that executes something; the check before the start compares the rows of the state with the declared names, and at run time the executor takes the current value of the datum, as in any expression (the expression is the same name, `—`). **The default expression** (AL-56): `—` in the cell “expression” means “the same name” — the expression of the field equals the field name (`| number | — | executor |` is the same as `| number | number | executor |`); this is not “no value”, and the sign is `—` because an empty cell is lost when editing and in viewers. With `—` the field name must be a name that the “Request” expressions read (a datum, a constant, a parameter, `input`, `party` for a set, for a party `machine` — `trace`, `step`), otherwise a check error, as for any expression. An explicit expression equal to the field name is allowed but not recommended: the check warns, the canonical form writes `—` (1b). The column “expression” stays even with `—` in all rows: table headers are not removed (markdown does not show a table without a header). The state rows, “On accept”, “Idle term” read **any** name from `Request`, whatever the value of `reads` is (T9). The request field `profile` is not written in the “Request”: it is given by the column `profile` of “Parties” (T3). The expressions read the machine data, constants, parameters, `input`, `party` (a set) and — for a party `machine` — `trace`, `step`; `call` reading is allowed (evaluated on entry, before sending, in the order of the rows). The request fields of a party `machine` are exactly the fields of its type `input`, except `profile` (it is given by the column of “Parties”, СВ5). A request field may be named as a datum with a different expression (`previous` — `require(previous)` of Pause): the rows, the conditions and “On accept” read the **datum**, not the field, the field is visible only to the party, and such a field is only `reads: party` (ША3); the expression of such a field is any “Request” expression, including `call` and `if` (in Changed of “Meeting” the field `proposal` is `if call(proposal_read) then { proposal } else { none }`), the rows do not read it (AL-28). The conditions, “On accept” and “Actions” read only the names from `Request`, `event.…`, bindings, constants and parameters (rule 11).
- **`reads` by default** (AL-27). If the source does not say who reads a field (its state “Input” table has no column “Who reads”), `party` is written: the field goes into the request, as in the source; `executor` — only for the names that the source names as not going into the request.
- **An appeal without request fields** (AL-23, AL-40). If the party needs no request fields (the gate “repeat / halt” without data), the line `Request:` and the table are not written: the request carries only what the executor gives (the envelope, `profile` from the column of “Parties”); the rows, “On accept” and “Idle term” of such a state do not read machine data — only `event.…`, bindings, constants and parameters. For a party `machine` a request without fields is allowed only if the type `input` has no fields (section 1, AL-30).
- **An appeal with free input** (AL-51, AL-52; rule 19). `Party` is a party of the kind `human` without a counter (section 1): there are no gates and no request, the executor sends and shows nothing, the machine waits for a word. Therefore such an appeal has no `Request`, `set`, `Idle term`, `Edits`, `Form returns`, no rows `response` and `failure` (the check of section 10); the rows are by the signals of the party (`signal(message { content, author, source })`); a word is accepted by the signal name in the current state, a word for which there is no row is discarded (rule 17); “human stop” is a common event (rule 23).
- **Idle term.** A line not written (an empty value `—` is not written, AL-40), `none` or `0` mean no term ( a human has no term — an open gate, rule 19; a gatekeeper has no term written in the state: the term of an agent gatekeeper is a parameter of the gatekeeper, rule 19; a machine call has no term, rule 35, item 5). The expression reads the same names as the “Request” expressions (data, constants, parameters, `input`, `party` of a set), without `call` (catalog functions are allowed, ША5); these names are named in the `Request` of the state (А7). It is evaluated on entry, after the “Request”, before the request is sent.
- **Edits** (E3, rule 14). `Edits: <datum>; check: <primitive>` — the party's response edits an object that the datum reflects (`proposal`), and the result cannot be accepted if the object changed since the beginning of the attempt. `check` is a reading primitive without parameters with the result `bool`; the executor calls it when it accepts the response, after the check of the openness of the request and the form and before `parse` and “On accept”. `true` — the result is not accepted (it is not written to `accepted_requests`, “On accept” is not executed, there is no event), the request is cancelled and goes out again: a new attempt, the `Request` is evaluated again; the journal entry about this is executor mechanics. The “beginning of the attempt” and the comparison are owned by the executor, the primitive reads its service record and the object (`reads`). A datum from `Edits` must be written in the “On accept” of this state (table check).
- **Set** (rule 21): `Party: lens; set: lens_order` — one request per identifier; `party` in the “Request” is the identifier for which the request is built; `Request limit` is a section of “Parties”. `to_send` is a datum `rows_and_mechanics`, `open_requests` is `mechanics` (section 2, СГ5), the party attempt counter is the column `counter` of “Parties” (section 1, СГ1).
- **Form returns** — how many times the executor returns to the party a response that is not by form or not by the comparison done by `parse` (for example, of excerpts; rule 18, СГ14). For the kinds other than `machine` — in the same request. For a party `machine` — with a new request of the same party with a new identifier and a remark: the same identifier would return the ready response (rules 14, 35, item 4). The comparison (for example, of excerpts) is done by the primitive `parse` on acceptance, the return itself is executor mechanics (E7). When the returns are exhausted, the request is closed by the event `failure` with the code `FormNotFixed` (a parse failure, section 1, AL-33).
- **Condition** in an event row — only for the common events and the signals of a fragment (rules 23, 35); for appeal rows `—`. An event whose condition is false is dropped (rule 17, the journal entry is mechanics). The condition `else` (E11) is allowed for a signal: the last row of the same event, taken if the conditions of the previous rows of this event are not true; the other events have no `else`.

### 4.4 On accept

The appeal block `On accept:` is a table `| event | actions |`. The event is `response`, `response(name)`, `response: Form { … }` or `failure`; the event bindings and `party` are available; the response value is the result of the party's `parse` (section 1). The executor executes the block when it accepts the response, before the transition, in one commit with the record in `accepted_requests` (rule 14); the bindings of the block (`let`) are saved with the accepted event and are visible to its row and chain. The order of acceptance: the openness of the request and the form, “Edits” (4.2), `parse`, the block.

Allowed in the block: assignments to data, `+=`, `field[key] = expr`, `field[key].field = expr` (5), `for`, `if`, `let name = expr` and `let name = call(reading, …)` (in any position of an expression, 3.1). Not allowed: `journal`, `machine_error`, `call` writing and irreversible, a transition; writing calls after acceptance (for example, a time mark and a cache check) are written in the row actions (АМ9). The data that the block writes are `writes: rows` (2).

## 5. Actions

The words of actions (`journal`, `machine_error`, `call`, `pass`, `cancel_open`, `for`) are quoted in the English form; the Russian form is in the [word table](alula-keywords.tsv), the kind `action` (1a).

A list through `;` in the order of writing (rule 29); **every action sees the results of the previous ones** (after `retry_count += 1` the journal reads the new value). The `call` actions of irreversible primitives are written in order but executed as the last stage of the commit, after saving (rule 13); their arguments are evaluated at the point of writing.

| Action | Meaning | Where |
|---|---|---|
| `field = expr`; `field += expr` | assignment; addition (int, f64, str, list) | rows, “On accept” |
| `field[key] = expr` | map: insertion or replacement; list: an existing index, otherwise a machine error | rows, “On accept” |
| `field[key].field = expr` | a short record of `field[key] = { ...field[key], field: expr }` (С11); no key — a machine error, the record is not created; a field with `writes: mechanics` — a check error. Where the source calls an absent key a program defect (`unreachable`, `required`), `field[key] = { ...require(field[key]), field: expr }` is written (4.4, Н-11) | rows, “On accept” |
| `field = without_key(field, key)`; `field = remove(field, element)` | removing a key and elements | rows, “On accept” |
| `journal(code, name: expr, …)` | a journal event: `code` is a Latin one from the template table, the parameter values are `str` | rows, “On entry” of an end, the body of `for` in the “On entry” of an end |
| `journal(value)` | an event assembled by `journal_event(…)` or `transition_note` | rows, “On entry” of an end |
| `journal(all_data)` | an abbreviation of `journal(machine_data, data: <data record>)`: the event `machine_data` with **one** parameter `data`; the encoding is below (И-2); the composition is in section 2. The name `all_data` in an expression is a record value (3.1) | “On entry” of ERROR |
| `let name = expr` | a binding until the end of “On entry” and for all rows of the state; also `let name = call(…)` | “On entry”, “On accept” |

| `if expr then { actions } [else { actions }]` | conditional (AL-70); the condition is an expression without `call` (catalog functions are allowed, ША5) | rows, “On accept”, “On entry” of an end |

| `pass(nested, signal)` | the signal `Signal` to the machines `nested` (a fragment parameter, section 9) from `open_requests` at the moment of the action (the addressees are taken at the point of writing, before the `cancel_open` of the same row), sent after the commit; the journal `signal_passed` for each (T4) | fragment only |

**A conditional action** (AL-70). The branches of a conditional action are written in braces, as a block in Nova: `if has(copy) then { proposal = require(copy) } else { journal(copy_restore_no_copy) }`; a branch holds one action or a list joined by `;`; `else { … }` is optional. The word `then` is required: the condition is an expression, an expression may end with a type name (`if x == Type.Var`), and the record `if x == Type { … }` would read as a comparison with a record or form literal `Type { … }`; `then` marks the end of the condition. A branch is not empty: a block `{ }` without content is a check error; an unneeded `else` branch of a conditional action is not written (for a conditional expression `else` is required). The conditional **expression** also writes its branches as blocks, one expression per block: `if expr then { expr } else { expr }`, `else` is required (3.1, AL-71); `then` is needed there for the same reason.

**The forms of `let`** (AL-73):

| Form | What it is | Where | Scope |
|---|---|---|---|
| `let name = expr` | a binding action | “On entry” of an operation, a fork and an end, “On accept” (outside a block) | until the end of “On entry” and for all rows of the state; in “On accept” — with the accepted event, its row and chain (2, “Lifetime of data”) |
| `let name = expr` inside `{ … }` | a binding action in a block | any action block: rows, “On accept”, “On entry” of an end, the branches of a conditional action, the body of `for` | up to the closing `}` of the block |
| `let name = expr;` inside a block expression `{ …; expr }` | a binding in a block expression (AL-75) | any expression position: a block body of a function, the branches of a conditional expression, expression cells | up to the closing `}` of the block |

`let` has no word `in` (removed in 2.18, AL-73, AL-75): a local binding in actions is the block `{ let name = expr; actions }`, in an expression — the block expression `{ let name = expr; expr }`.

**Product journal codes** (AL-31). The code in `journal(code, …)` and `machine_error(code, …)` is taken from the template table of the [journal](state-machine-journal.md) (section 2 and the subsection “Events of the table format”) — these are the methodology codes. A product that needs its own events (a record of executor mechanics: an edit of a response under “Edits”, a form return, a request repetition, an order of a signal — for example `answer_edited`, `form_returned`, `request_repeated`, `signal_ordered`) declares them by a **product template table** of the same form (`Machine | Event code | Russian template | Parameters`) next to the methodology table; where it lies is named by the host registry (as the functions files, section 8). Rules: a product code is a Latin `snake_case` by the rules of a journal code; it does not repeat a methodology code (a coincidence is a check error, even with the same template); a code that the format itself or the contract mechanics writes (`signal_passed` of `pass`, `input_rejected`, `machine_error`, `machine_data`, the codes of the “Pause” fragment) is not replaced by the product with its own code: its own event (for example, `signal_ordered` when a signal is ordered before the commit) is written next to the methodology code, not instead of it. The check (section 10) compares the code and the parameters of a row with the union of the two tables; a code outside the union is an error. The methodology script [check-tables.py](check-tables.py) reads only the methodology table; the product table is read by the product check. Product codes are not entered into the methodology table.

**Encoding of `journal(all_data)`** (И-2; ША1; checked by an implementation). The event `machine_data` with **one** parameter `data`. The parameter value is pairs `name=value` (the name is the JSON name of the datum, 1a), the separator is `; ` (a semicolon and a space); the order is the order of the rows of the “Data” table of the machine (first the data of the included fragments in the order of inclusion, then the data of the machine); field paths inside a map (`name[*].field`) are not in the composition — they are part of the map value. The value of a pair:

| Value | Record |
|---|---|
| integer | decimal record |
| f64 | `text(x)` (the shortest reversible record, an integral one with `.0`; 3.3) |
| text, literal set, `id` | as is, without quotes; empty text is empty after `=` (`stop=`) |
| `bool` | `yes`, `no` |
| optional `none` | `none` |
| enumeration | the value of the element (the Latin text of the code); for an element without a value — its JSON name (AL-15, AL-46) |
| `State` | the JSON name of the state |
| list | a JSON array `[…]`; empty is `[]` |
| map | a JSON object `{…}`; empty is `{}`; for a map with non-text keys — an array of pairs `[[key,value],…]` in the order of the first write of the key |
| record | a JSON object; the keys are the JSON names of the fields, the order is the order of the type's fields |
| enumeration with fields | a form with fields — `{"Var":{fields}}`; without fields — the string `"Var"` (JSON names) |
| tuple | an array; positions in order |

Composite values are encoded in JSON without loss: without spaces (the separators `,` and `:`), UTF-8, non-ASCII signs are not escaped, text escaping is by RFC 8259 (`\"`, `\\`, `\b`, `\f`, `\n`, `\r`, `\t`, other control signs — `\u00xx` in lowercase); inside a composite, text is a JSON string, `none` is `null`, `bool` is `true`, `false`, float is a number by `text(x)`, an enumeration and `State` are a string by the table rows. Encoding and parsing back and forth are without loss: Cyrillic and 4-byte letters are preserved, integer and float are distinguished (`1` and `1.0`). An integer (`int`, i64) in JSON is a number: values above 2^53 in magnitude may lose precision in JSON readers that store numbers as f64 (AL-101).

Examples (`data=` is the name of the event parameter): `data=count=0; label=abc; began=1000; log=[]; table={}; stop=` and `data=total=99; label=; log=[]; counts={}; items={}; p_attempt=0`; the map `lenses map[str, Lens]` (the fields of `Lens` with the JSON names `id`, `lost`, `probes`, `attempt`) — `lenses={"l1":{"id":"l1","lost":0,"probes":0,"attempt":2}}`; `turn_before_retry=none` — an empty optional `turn_before_retry` (in the Russian sample the datum `ход_до_повтора`, its JSON name is automatic).

## 6. JSON tree

**The file name of the tree** (AL-19). A tree compiled from `<name>.alula.md` lies next to it in `<name>.alula.json` (`agent_step.alula.md` ↔ `agent_step.alula.json`). JSON is the executable form of the language itself, not another format: a hand-written tree is also Alula in the JSON form; the key `format: "machine/2"` inside the tree does not change. The former name `*.machine.json` is not used and loading does not accept it (AL-22). The rules by which a tree is written back to an Alula file are in section 1b.

**The language version in the tree** (AL-108). The root of the tree carries the key `alula_version` — the format version with which the tree was compiled (a string; for this version — `"2.22"`); the key is optional: without it the tree is of the version that the program reads. A program reads exactly one format version: a tree with another `alula_version` is an error whose message names the version (there is no transition period). The key `format` (`"machine/2"`) is the tree format, it does not depend on the language version; there is no key `table_format` (the former text of 1b (a) named this key so).

The JSON tree and its schema are outside this file: the schemas of the tree (`machine/2`) and of the scenarios (`scenario/0`) live in the repository of the language, [nv-lang/nova-alula, folder `src/machine/schema/`](https://github.com/nv-lang/nova-alula/tree/main/src/machine/schema); the schema version is kept by the package `alula`, the keys in it are English; the schema is the first source of the structure of the tree, this file is the source of the rules of the record and of the correspondence of words to keys. The tree is the same for a Russian and an English file: the words of both languages correspond to one key and one value (the word table, 1a); the party kind “human or agent by setting” is called `gatekeeper` in the tree (section 1). ## 7. Primitive registry and admissibility of classes

A registry entry: `name`, `parameters` with types, `result`, `class`, `reads`, `writes`, a note. The JSON name of a primitive is the name in the host registry: for a non-Latin name it is built automatically (1a, AL-53; `профиль_стороны` → `party_profile` by the glossary), and if the registry name is different it is set by a `## Names` row (AL-60). Pure functions over data are written not here but in “Functions”; text parsing, reading objects, time, closing a turn, effects remain primitives.

| Class | What it does | The call `call(name, …)` is allowed |
|---|---|---|
| `pure` | a pure host function | as a function `name(arg)` everywhere |
| `reading` | reads an object, a store, time; does not change machine data | in the “Request” of an appeal, in `profile`, in `let` of “On entry” (operations, forks, ends) and “On accept” (in any position of an expression, 3.1), as `parse` of a party `machine` and `check` of the property “Edits” (4.2); not in conditions and not in row actions; `new_id` — only in `let` of the “On entry” of an operation (below) |
| `writing` | writes inside the commit (machine data, objects, a buffer) | in the “On entry” of an operation and an end (including `let name = call(…)`) and in row actions; not in conditions, not in the “Request”, not in the “On entry” of a fork |
| `irreversible` | an external action that cannot be rolled back; the last stage of the commit, repeatable without harm (rule 13) | where `writing` is |

- `reads:` — machine data, objects, service records that the primitive reads hidden (not through arguments). These names enter the reads of the state (`Request`, `Reads`) at the point of the call (rule 11).
- `writes:` for `writing` — the machine data that the primitive changes in place; the check “writes ⊆ data” counts it. For `reading` — only service records of the executor (not machine data, not objects); the record names who reads it (the primitive or the turn mechanics) so that the dependence is visible (for example, the remarks of the form check for the turn “fix”).

**Result by role** (Н-12). **A function without a body in the source** (ИС6, Н-3, Н-4; decision of the methodology, 2026-10-19): a function that has no body in the source (in the automaton code only a signature) is written as a **host primitive** with a class and a description by the tables of the primary source; it will become a function in the language when the body appears in the source (then the record is moved to `## Functions`). One rule for all such functions, pure or not; **the class is by the signature of the source**: a free function without `mut` and without `Objects` is `pure` (called as `name(arg)` everywhere); a method of machine data without `mut` or a function with `Objects` without `mut` is `reading` (reads data or objects, changes nothing); with `mut` — `writing` (writes data, objects or a buffer); `irreversible` is not derived from a signature, it is named by the body or a comment of the source. The pilot count counts such functions as written as primitives. Bodies are not entered into the automata by this.

## 8. Functions, constants, parameters

**A function** (the declaration `fn`, Russian `функция`; AL-83) is a pure function of the author, its body is one of two (AL-84, as in Nova): `fn name(arg type, …) -> type => expr` is a body of one expression; `fn name(arg type, …) -> type { let name = expr; …; expr }` is a block body: zero or more bindings `let name = expr;` and lastly one expression, its value is the value of the function (AL-75). `=>` and `{ … }` are not combined: `=> {` after a header is a check error; after `=>` stands one expression, a multi-line one included (`if … then { … } else { … }`, `match … { … }`), and `{` after the result type always opens a block body, so a record copy as the whole body is written in parentheses: `=> ({ ...r, field: expr })`; an empty block body is an error. A `match` branch is the exception, as Nova's `match` arm: `alt => expr`, `alt => { let …; expr }` included (3.1). A “function” without a qualifier in this specification is an author function; the functions of section 12 are catalog functions. Arity 0 is allowed; there is no recursion. A constant is a named value with a type. A parameter is a default value and a project override (`project.<key>`).

Example (pilots; changed: `usage_event` instead of the event function of the code, a tuple key instead of the pilot's record; `yes_no_word` — for the values of journal parameters, 4.7; `merge_unique` is removed: it has no body in the source, it is a host primitive, section 7, Н-4).

  if has(a) and has(b) then { (a ?? 0) + (b ?? 0) } else { a ?? b }

fn yes_no_word(b bool) -> str =>

```

**Functions files** (С30). Functions common to several machines lie in an included file and are included by a line of the section `## Includes`:

```
functions: <name> version <N> hash <hex12>
```

- **Registry** (СГ4, СЖ4). `<name>` is the name of the functions file by the registry of included files (not a path). The registry is part of the host registry, the same one where the primitives (section 7) and the machines (rule 35, [call protocol](state-machine-call-protocol.md), section J, item 6) are written: an entry `name → file` (a path relative to the registry). The format of the registry file is set by the host; the table format requires one thing: exactly one file is found by name, otherwise it is a table check error.
- **The header of a functions file:** `# Functions: <name>`, list items `- functions_version: <N>` (an integer), `- format: 2.22` and optionally `- language: ru`/`en` (1a). The `version` of the include line must match `functions_version` exactly.
- **Sections** — `## Types`, `## Constants`, `## Functions` in order, **all three are required**; an empty section is the line `—`; the optional `## Names` (1a, AL-60) — after `## Types`, only if it has rows. Only pure functions, types and constants; without `## States`, without `call` of the classes reading, writing, irreversible, without `## Includes`: a functions file does not include other files (there are no cycles by construction).
- **Hash** — the first 12 signs of the SHA-256 of the file content in UTF-8 after normalization (Н-8): a leading BOM is dropped (a file with and without a BOM give one hash); line breaks are LF (CRLF and a lone CR are replaced by LF); trailing spaces and tabs are removed from every line; at the end of the file there is exactly one LF (empty lines at the end are removed, a missing LF is added); the 12 signs of the hash are hexadecimal, in lowercase. The normalization is unambiguous: a file without a final LF and a file with it give one hash.
- Names from an included file are visible without a prefix; a coincidence with a local name or with a name of another included file is a table check error; a mismatch of the version or the hash is a table check error, not a warning.

## 9. Included fragments

A fragment (rule 36) is a file of the format `fragment`: the header `# Fragment: <Name>`, list items `- fragment: <latin_name>`, `- format: 2.22` (optionally `- language: ru`/`en`, 1a) and sections in order: `## Parameters`, `## Requires`, `## Data`, the optional `## Names` (1a, AL-60), `## Common events`, `## States`. In the text a parameter stands as `<parameter>` and is substituted before the check (rule 34).

**Parameters** — `name`, `kind`, allowed values. The kinds (not data types; the group `kind_param` of the word table, AL-63): `signal` (a party signal, AL-38), `str`, `[]machine` (a list of names of nested machines; this is a kind, there is no type `machine`), `behavior` (a closed list of fragment words; the meaning is the executor's description in the fragment text), `note` (text for the reader). An include names all parameters; an omitted one is an error.

**Requires** — what the fragment requires from the machine: the values of `stop_reason`, the rows of “Ends”, the ends Halted and Errored, the party `enhanced` of kind `enhanced` in “Parties” with the signals `continue { human_word str, author str, source str }` and `<halt_signal>` (Pause addresses it); the value `previous` is always an appeal: the machine stands only in appeals and ends, and in the ends and in Pause the COMMON 1 and 2 are dropped by a condition (rule 24; ШМ2).

**Names of the fragment:** `state` (the current state, type `State`), `previous` (`?State`), `call_request_id` (text; the identifier of the request by which the machine was started is given by the executor), `event.id`, `end(state)` (catalog), `nested`. `state` is an executor name (type `State`); `previous` (`?State`) and `call_request_id` (text; the identifier of the request by which the machine was started, the value is set by the executor at the start) are **data of the fragment** (the “Data” table below), not executor names (T6). The common events read the data of the fragment, `state` and `event.…` without a reads line; the states of the fragment — only their own reads (`Request`, `Reads`).

**Values of parameters of the kind `behavior`** (А5, E10) are closed lists of words; a value outside the list is a check error. The effect is named formally and applied where indicated; `write_right` is a note for the reader, the executor does not evaluate it.

## 11. Scenarios

A scenario is events and an expectation: an event (`start` with input, `response`, `failure`, `signal` of a party or of the machine with data, a term) → the state, the structured journal (code and parameters, rule 31), a subset of data, the queue. The comparison is by these four; the runner is in the product; the same scenario is run on the methodology automaton. The form of a scenario record is in general not set here (the runner format is in the product); the format fixes three things. **The file name** (AL-20): a scenario (`scenario/0`) is called `<name>.scenario.test.json`; the scenario format does not change. **Event data** (П-8): a signal (of a party or of the machine) with one data field carries the value of that field — text (for example, `continue` with the field `author` — the value `"ivan"`, not an object); with several fields — an object `{field: value}`; without fields — only the name. **Parameters** (П-9): a scenario may carry `params` — a “key → value” table with the keys `project.<key>` (section 1, “passing values from outside”); a parameter not named keeps its default value.
