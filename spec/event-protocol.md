# Контракт событий Алулы

**Статус: опытный контракт, профиль `alula.events/2`, не реализованный production backend.**
Версия профиля не является версией языка или пакета. Эта правка не меняет выпуск 0.28,
не подключает протокол к движку и не реализует сетевые адаптеры. Термины языка —
[спецификация Алулы](alula-spec.md). Согласовано владельцем направление работ,
2026-10-30, чат Методики: «по рекомендации, супер быстро»; правила ниже требуют
независимой проверки до внедрения. Ожидаемая ошибка без контракта: сигнал доставлен,
но его повтор, неверные данные или чужое решение незаметно меняют результат машины.

## 1. Охват и соответствие

Здесь первоисточник формы и приёма событий экземпляра: сигналы сторон, управление
родителя, ответы и отказы по запросам; приём отделён от выполнения перехода.
Это не ещё один транспорт: локальный API и внешние bindings исполняют одни операции.
Опытный методический `state-machine-call-protocol.md`, версия 1, описывает другой,
более ранний охват. Совместимость с ним **не заявляется**; автоматического fallback,
смешивания конвертов и изменения старого документа этой правкой нет.

Готовая реализация соответствует профилю, только если исполняет все нормы этого
файла и проходит проверки на собственном хранилище, движке и каждом заявленном binding.
[Модель](../tools/event_protocol_model.py) и [её тесты](../tools/test_event_protocol.py)
проверяют отдельные свойства контракта, **не соответствие существующего движка**.
Они не подтверждают fsync, транзакции БД, авторизацию или безопасное выполнение эффекта.

## 2. Контракт, сборка и открытые действия

Компилятор должен экспортировать manifest из того же проверенного определения,
которое исполняет движок: раскрытые типы, технические имена, стороны, сигналы и их
поля, результаты запросов, версию codec. Ручная копия этих объявлений запрещена.
Экспорт manifest в этом этапе **не реализован**; manifest тестов — явная фикстура.

- `contract_id` — SHA-256 канонического публичного manifest, включая codec.
- `artifact_id` — отдельно закреплённая сборка: машина, библиотеки, реестры и
  семантическая версия исполнителя, в том числе правила применимости и арбитража.
- Авторский `revision` не заменяет ни один из этих идентификаторов.
- Экземпляр закрепляет оба идентификатора на всю жизнь. Горячая замена запрещена;
  миграция активного экземпляра требует отдельного утверждённого контракта.
- `instance.describe` даёт доступную principal проекцию текущих действий и ворот.
  Это подсказка с версией наблюдения, а не разрешение и не обещание будущего приёма.

Хозяин при несовпадении закреплённой сборки останавливает восстановление, а не берёт
«последнюю» совместимую на вид версию. Идентификатор экземпляра не переиспользуется.

## 3. Значения и канонизация

`data` всегда объект: `{}` при отсутствии полей, объект с одним полем при одном поле.
Неизвестные поля и повторные JSON-ключи — отказ; текст не обрезается и Unicode не
нормализуется молча. Все поля записи обязательны; отсутствие optional задаётся явно.
Ограничения типов проверяются, а не исправляются приведением значения.

| Тип manifest | Кодирование `alula-json/2` |
|---|---|
| `str`, `bool` | JSON-строка, JSON-булево без преобразований |
| `i64` | каноническая десятичная строка в диапазоне знакового 64-битного числа; без `+`, ведущих нулей и `-0` |
| `f64` | строка из 16 строчных hex-цифр: биты IEEE 754 binary64 в порядке от старшего байта; сохраняет `-0`, бесконечности и payload NaN |
| `id` | UUID: 8-4-4-4-12 строчных шестнадцатеричных знаков |
| запись | объект полей по техническим именам, без runtime-тегов |
| кортеж | массив фиксированной длины |
| список | массив элементов |
| словарь | массив пар `[ключ, значение]`, в значимом порядке Алулы; одинаковые ключи запрещены |
| optional | `{"none":true}` либо `{"some":значение}`; сохраняет вложенные optional |
| перечисление / форма | `{"case":"техническое_имя","fields":{...}}`, в том числе пустой `fields` |

**Открытое решение владельца.** Для `f64` и канонических байтов ниже записан точный
кандидат черновика, но владелец не утверждал эти детали отдельно. До такого решения
они не являются подтверждённым межреализационным codec: нельзя заявлять совместимость
независимых encoder/decoder или допускать профиль в production. Остальные требования
раздела — опытный контракт этого этапа.

Manifest задаёт ограничения строковых наборов, числовых границ и полноту `full_map`.
Словарь не преобразуется в JSON-объект даже при строковых ключах. Канонические байты:
UTF-8 без BOM, без пробелов вне строк, ключи объектов сортируются по Unicode code point,
строки сохраняются без ASCII-экранирования (экранируются JSON-кавычка, обратная косая
и управляющие U+0000–001F; для последних — строчное `\u00xx`, кроме `\b\t\n\f\r`).
Нельзя сортировать массивы: это разрушило бы порядок словаря. Дробные JSON-числа
профиль не использует; целые метаданные ограничены диапазоном точных целых JSON-клиента.

## 4. Конверты

Общие обязательные поля: `event_id`, `instance_id`, `contract_id`, `kind`, `data`.
Идентификаторы события и экземпляра — непустые ограниченные строки; UUID допустим,
но версия UUID не навязывается. `event_id` обозначает логическое событие, не RPC-вызов.
Необъявленные поля конверта запрещены. Обязательность остальных полей определяется видом:

| kind | Обязательные дополнительные поля | Значение |
|---|---|---|
| `party.signal` | `party`, `signal`; для ворот `gate_id` и, если ворота о предмете, `subject_id` | сигнал конкретной стороны |
| `machine.control` | `signal`; у родителя `request_id`, при продолжении паузы также `pause_id` | разрешённая управляющая операция, не обход ворот |
| `request.reply` | `party`, `request_id` | `data` ровно `{"result":значение}` объявленного типа |
| `request.failure` | `party`, `request_id` | `data` ровно `{"code":"код","message":"текст"}`; код из контракта отказов |

Поля другого вида не допускаются. В частности, reply не превращается в сигнал без
корреляции. Для свободного ввода нет `gate_id` и `subject_id`.
Запись ворот связывает ID с экземпляром, стороной, закреплённым контрактом и неизменным
предметом решения. Переоткрытие даёт новый ID; восстановление тех же ворот — прежний.
Родительский `request_id` проверяется по действующей связи с родителем, `pause_id` —
по конкретному открытию паузы. Старое continue не может снять другую паузу.

Пример полезной нагрузки `event.submit` (имена из экспортированного контракта):

```json
{"event_id":"decision-17","instance_id":"run-9","contract_id":"sha256:…","kind":"party.signal","party":"gatekeeper","signal":"confirm","gate_id":"gatekeeper-42","subject_id":"proposal-hash","data":{"comment":"Согласовано"}}
```

## 5. Доверие и приём

Principal, tenant и устойчивый `producer_id` даёт аутентифицированный хозяин, а не
payload. Поля `author`, `origin`, `party` и знание ID ворот не удостоверяют личность.
Хозяин проверяет полномочия на экземпляр, сторону и действие до выдачи receipt и
повторно при admission, если политика могла измениться. Отзыв прав не обходит dedup.
Статус существующего события также доступен только уполномоченному principal.

Сигнал разрешается по `(kind, party, signal)`, не по первому совпадению имени.
Неверные типы, неизвестные поля, чужой запрос, закрытые ворота, неверный предмет и
неприменимое состояние не закрывают запрос/ворота и не изменяют предметные данные.
Непринятый сигнал не сохраняется до следующего похожего состояния. Принятое событие,
ожидающее перехода, сохраняется через паузу и восстановление по правилам машины.

Человеческие continue/halt в ПАУЗЕ остаются словами её ворот. Их нельзя заменить
безусловным `machine.control`. Контроль родителя — отдельное полномочие и корреляция.
Общие строки проверяются первыми **для данного события**; глобального приоритета
всех controls над очередью нет. Неизвестная схема отклоняется без попытки угадать её.

## 6. Receipt: статусы и переходы

| status | Терминален | Гарантия |
|---|---|---|
| `queued` | нет | событие долговечно записано, предметный приём ещё не обещан |
| `accepted` | нет | admission выполнен и решение зарезервировано, переход ещё не зафиксирован |
| `applied` | да | переход, состояние и intents зафиксированы, внешние эффекты могут ещё выполняться |
| `rejected` | да | предметный приём отклонён с кодом и, для данных, путём ошибки |
| `superseded` | да | принятое решение агента вытеснено человеком; есть ссылка `replaced_by` |
| `cancelled` | да | ожидающее событие окончательно снято по политике машины, не доказательство отмены внешнего эффекта |

Таблица ниже — первоисточник допустимых изменений статуса; модель читает её, а не
держит вторую копию. `none` — отсутствие записи, не публичный статус.

<!-- receipt-transitions -->
| from | operation | to |
|---|---|---|
| none | submit | queued |
| queued | admit | accepted |
| queued | reject | rejected |
| queued | cancel | cancelled |
| accepted | apply | applied |
| accepted | replace | superseded |
| accepted | cancel | cancelled |
<!-- /receipt-transitions -->

Терминальные статусы неизменны. Повтор возвращает **текущее** состояние receipt,
а не первоначальный ACK. `accepted` выставляется только при отдельном долговечном
решении арбитра. Синхронная реализация может объединить admission и apply одной
транзакцией; промежуточный accepted тогда не обязан быть видим клиенту.
Публичные receipt содержат `event_id`, `instance_id`, `status`, монотонный `version`,
серверный `seq`; у отказа `code` и при наличии `path`, у замены `replaced_by`.

## 7. Арбитраж, порядок и фиксация

У экземпляра один сериализованный исполнитель либо эквивалентная согласованная
реализация. `seq` присваивает долговечная запись хозяина; часы клиента не определяют
порядок. Глобальные часы, vector clocks и producer sequence не требуются.

1. **Ingress:** проверить конверт/лимиты/полномочия, dedup; сохранить inbox и queued
   до подтверждения. Сбой сохранения не выдаётся за queued.
2. **Admission:** проверить pinned contract, форму, актуальные права, применимость,
   корреляцию; одной фиксацией записать accepted/rejected, выбранное решение ворот,
   версию выбора и предусмотренные записи приёма.
3. **Apply:** перепроверить выбранное решение и входную очередь в той же
   сериализованной границе commit; записать новое состояние, applied, закрытие
   ворот/запроса, журнал и outbox intents атомарно либо эквивалентным WAL/replay.
4. **Dispatch:** выполнить intents отдельно с устойчивыми `effect_id`; журналировать
   исход и неопределённый результат. Эффект не считается успешным по факту отправки.

До commit перехода все уже записанные queued события до захваченной границы inbox,
способные заменить решение текущих ворот, должны пройти admission по порядку.
Новое поступление меняет версию inbox: вычисленный переход с прежней версией
не фиксируется и переоценивается. Это не обещает успеха неверному queued слову.

**Два окна.** Человек раньше admission ответа агента занимает ворота, запрос агенту
отменяется; поздний ответ отбрасывается. Если агент уже accepted, но переход ещё
не committed, admission человека атомарно выбирает его и делает агента superseded.
Apply проверяет версию выбора. После commit человеческое слово отвергается как
слово закрытых ворот, без отката. В ПАУЗЕ принятые решения сохраняются; их замена
человеком имеет те же условия, но переход приостановленной работы не выполняется.
Gate admission не выполняет необратимых предметных эффектов, требующих отката при
замене. Нормативные «При приёме» других ответов не объявляются этим безэффектными:
реализация обязана отдельно согласовать их транзакционность, не повторять при recovery.

`applied` гарантирует однократную фиксацию перехода данного события, **не exactly-once
внешнего эффекта**. Для эффекта нужны идемпотентный получатель/предметный ключ либо
сверка результата; при отсутствии обоих автоматический повтор необратимого действия
запрещён, хозяин останавливает dispatch с явным неопределённым исходом.

## 8. Dedup и хранение

Ключ: `(tenant, instance_id, trusted producer_id, event_id)`. Producer переживает
reconnect и смену credentials. `contract_id` не часть ключа. Хеш предметного
содержимого включает контракт, адресата, корреляцию, preconditions и data; RPC ID и
время повторной доставки не входят. Другая нагрузка с тем же ключом —
`event_id_conflict`, без новой записи/применения. Авторизация выполняется и для повтора.

Пока экземпляр активен, dedup не удаляется по TTL. После завершения хозяин публикует
срок хранения receipt и персональных данных; по его истечении выдаёт `status_gone`,
а не разрешение применить событие заново. Сохраняется tombstone или эквивалентный
watermark, запрещающий повтор; завершённый ID экземпляра не открывается повторно.
Сроки и лимиты — явно объявленные параметры развёртывания; отсутствие значений
блокирует production-допуск. Хранение хеша не разрешает хранить лишние тексты бессрочно.

## 9. Операции, ошибки и bindings

- `contract.get`: доступный публичный manifest и codec по закреплённому ID.
- `instance.describe`: текущая авторизованная проекция действий, ворот и версии.
- `event.submit`: надёжная отправка; ответ receipt, не обещание перехода.
- `event.status`: текущее receipt либо `not_found`/`status_gone` без утечки чужих данных.

Локальный API исполняет те же операции без сериализации и handshake. Внешний профиль —
JSON-RPC 2.0, версия `alula.events/2` согласуется до submit; неизвестная версия — отказ.
Submit — **request**, не notification: notification не подтверждает даже ошибку.
Повтор может иметь новый RPC ID и прежний event_id. Уведомления состояния допустимы
как подсказки, но источником истины остаётся `event.status` с версией receipt.

| Уровень | Ответ |
|---|---|
| Неверный JSON/RPC/структура params | ошибка JSON-RPC, не предметный receipt |
| Валидное событие, неверные typed data/ворота/применимость | `rejected`, стабильный код и путь поля |
| Отказ работы стороны | `request.failure`, а не ошибка вызова event.submit |
| Потеря ответа, 5xx, обрыв | исход неизвестен; status или повтор того же event_id |
| Перегрузка до durable ingress | явный отказ с retry advice, не queued |

HTTP binding после допуска endpoint возвращает JSON-RPC result/error с HTTP 200;
401/403, 413 и 429 до durable ingress разрешены. HTTP 202 не является второй моделью
receipt. WebSocket передаёт один JSON-RPC объект сообщением; stdio — UTF-8 JSON Lines,
один объект строкой. Batch в профиле не поддерживается; после разрыва нет предположения
о доставке. Таймаут RPC не отменяет событие. Хозяин объявляет ограничения байтов,
глубины, очередей и скорости; принятые события не выкидываются из-за backpressure.
Нельзя в одном binding считать событие принятым раньше, чем в другом.

## 10. Допуск к production

До допуска нужны экспорт реального manifest, полный codec, аутентификация и политика
прав, долговечный inbox/receipts/реестр ворот, атомарный apply/outbox, recovery и
заявленные bindings. Обязательные пробы на **самой реализации**, не только модели:

- одинаковое имя сигнала у двух сторон, неверные/лишние поля и duplicate JSON keys;
- точность i64, биты f64, порядок/дубли словаря, full_map, вложенные optional;
- оба окна человека, ПАУЗА, гонка admission/commit и старое continue против новой паузы;
- неверный тип reply оставляет запрос открытым, включая recovery и последующий верный reply;
- потеря ACK, идентичный повтор, конфликт payload/контракта при том же event_id;
- падение между каждым долговечным этапом, восстановление выбранного решения и outbox;
- срок хранения без повторного применения, смена credentials без обхода dedup;
- отказ при чужой сборке/контракте, эквивалентные исходы HTTP/WS/stdio;
- неизвестный исход внешнего эффекта без ложного успеха/слепого повторения.

Диагноз о преждевременном закрытии reply в прежнем движке — вывод по коду, не
подтверждённый этим этапом runtime-дефект актуального выпуска. Его требует проверить
названная проба. Зелёные тесты модели не разрешают объявить существующий runtime
соответствующим этому профилю или включить профиль в опубликованный выпуск.
