# Как отлаживать Алулу

Черновик. Команды сверены с программой `alula` пакета [nova-alula](https://github.com/nv-lang/nova-alula) (v0.3.0) её разработчиком; после выхода 0.3.1 они проверяются ещё раз. Что делает язык — [alula-overview.md](alula-overview.md); спецификация — [state-machine-alula-spec.md](state-machine-alula-spec.md).

**Одним абзацем.** Отлаживают в три слоя: сначала запись (разбор и проверки), потом перевод в дерево, потом поведение (сценарий и журнал). Пошагового отладчика с остановками нет: машина исполняется шагами, каждый шаг — одна фиксация, и после шага можно сравнить всё, что он оставил, с ожидаемым.

## 1. Запись: `check`, `summary`

```
alula check   машина.alula.md
alula summary машина.alula.md
```

- `check` разбирает файл и проверяет таблицы. Пишет `ok` (или `ok (N warnings)`) и код 0, если ошибок нет. Ошибка выглядит так: `файл:строка:столбец: вид: сообщение`, под ней цитата строки. Проверки таблиц называют строку, из которой пришли. Предупреждения идут в том же виде и код выхода не меняют.
- `summary` печатает, что переводчик понял: состояния с видами (операция, обращение, развилка, конец), число строк и действий, данные, стороны. Если состояние не того вида или стороны нет в списке, ошибка в записи, а не в логике.
- Файл `.alula.json` тоже принимают оба: у JSON нет строк, место называет путь к узлу (`$.states[0].rows[1]`).
- `--no-check` пропускает проверки таблицы против примитивов хозяина: нужно, когда проверяется только разбор.

## 2. Дерево: `compile`, `render`, `convert`

```
alula compile машина.alula.md -o машина.alula.json
alula render  машина.alula.json --language en -o машина.en.alula.md
alula convert машина.alula.md --language en -o машина.en.alula.md
```

- `compile` строит дерево `machine/2`. Запись → дерево → запись (`render`) должна возвращать ту же машину: если после `compile` и `render` текст выглядит не так, как ждёшь, смысл разошёлся при переводе, а не в машине.
- `convert` = `compile` + `render` на другой язык (ru ↔ en). Комментарии через дерево не проходят — программа говорит об этом на стандартном потоке ошибок.
- Существующий файл `-o` без `--force` не перезаписывается; при ошибках файл не пишется (кроме `--lenient`).

## 3. Поведение: сценарий и журнал

Сценарий (`scenario/0`) — JSON-файл `*.scenario.test.json`: машина, начальное время и список шагов. Шаг подаёт одно событие и описывает, что машина должна оставить после шага.

```
alula run  машина.alula.json сценарий.scenario.test.json     # один сценарий
alula test папка [-v]                                         # все сценарии папки и подпапок
```

Шаг сценария (поля):

| Поле | Что значит |
|---|---|
| `do` | `feed` (по умолчанию: подать событие), `accept`, `dispatch`, `pump`, `deliver`, `advance` (сдвинуть часы на `ms`), `restart` (перезапуск: повторный вход в сохранённое состояние) |
| `event` | событие: `kind` — `word`, `signal`, `progress`, `answer`, `failure`, `timeout`, `start`; `name`, `request` (идентификатор запроса), `input` |
| `host` | ответы примитивов хозяина, которые действуют с этого шага (например, результат проверки ответа) |
| `expect` | что должно остаться: `state`; `journal` (список `{code, params}` — строки журнала, записанные шагом); `data` (подмножество данных по именам); `open` — открытые запросы; `sent`, `cancelled` — все отправленные и отменённые запросы; `queue`; `outcome` (`none`, `answer:<текст>`, `refusal:<код>`) |
| `on`, `also` | для вложенных машин: на каком запросе действовать и что должны оставить другие движки |

Что не названо в `expect`, не сравнивается. Поэтому сценарий для отладки начинают узким: `state` и `journal`, остальное добавляют, когда нужно.

**Чтение результата.** `run` печатает `ok` и код 0 либо отчёт о первых различиях и код 1. Различие называет шаг и поле: `step 2 (feed): state: expected Failed, got Done` — значит, второй шаг привёл машину не в то состояние. `test` печатает такие отчёты по каждому расходящемуся сценарию и итог `N of M scenarios passed`; `-v` добавляет строку `ok <файл>` по каждому сценарию.

**Журнал — главный инструмент.** Чтобы понять, по какой строке машина пошла, смотрят коды журнала: каждое действие `журнал(код, …)` оставляет запись, шаблоны текста лежат отдельно. Сценарий проверяет журнал через `expect.journal`. Если ожидаемого кода нет, а есть другой, пошла другая строка таблицы.

## Типичный порядок

1. `check` — запись цела. Исправить ошибки сверху вниз: первая часто порождает остальные.
2. `summary` — машина состоит из того, что имелось в виду.
3. Написать сценарий, воспроизводящий неверное поведение, с узким `expect` (`state`, `journal`).
4. `run` — найти шаг, где ожидание расходится.
5. Посмотреть строки состояния в таблице: условие, действие, «Куда». Если строка с нужным условием не взята, вмешался порядок строк или общее событие.
6. Исправить, `test` по папке — убедиться, что остальные сценарии прошли.

## Чего нет

- Флага `--verbose`/`--trace`, вывода журнала или взятых строк у `run`: журнал проверяется ожиданием в шаге сценария, построчной трассы нет (взятые строки интерпретатор хранит как `Состояние#N`; вывод в программу — возможная будущая задача).
- Остановки посреди шага: шаг — одна фиксация.
- Машина с вложенными машинами не запускается через `run` (код 1, подсказка использовать `test папка`); сценарий с `"standalone": true` играет стороны сам.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | успех (предупреждения допустимы); `alula` без аргументов печатает справку |
| 1 | ошибки в файле, сценарий расходится с машиной, примечание `render` |
| 2 | неверная команда или аргументы, нечитаемый файл, существующий `-o` без `--force`, папка без сценариев |
