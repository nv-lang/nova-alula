# План эпика 019: Алула 0.29

**Тип: эпик. Статус: проект плана.** Цель, границы, обследование и реестр REQ — в [spec.md](spec.md). Карточки A–H ниже — кандидаты, не зарегистрированные задачи и не разрешение реализации. Все пути исходников в карточках указаны от корня репозитория.

## Дочерние результаты-кандидаты

Оценки — грубые рабочие дни по 8 часов на реализацию и её собственные проверки, не обещание срока; их уточнить при заведении задач после принятия эпика. Каждый результат принимается отдельно по изменённому коду и проверкам. Все отрицательные пробы должны показывать точную причину отказа, а не только ненулевой код.

В таблице R1–R8 — REQ coverage; AC каждого результата — перечисленные в его строке положительные и отрицательные проверки плюс независимый прогон указанного subsystem. Итоговые сквозные AC-E1–AC-E4 заданы ниже. Суммарная оценка 23–45 дней, 184–360 часов без ожиданий и независимой приёмки; весь эпик не является малой задачей ≤30 минут. Оценка подготовки самого плана до правок — T≈15 минут.

### Безопасный порядок и параллелизм

Обязательные runtime AC-D (владелец — D, trusted host hooks — E):

- **AC-D1:** `call` различает progress и terminal reply; progress не закрывает запрос; withdrawal прекращает ожидание, cancel запрашивает остановку и не доказывает компенсацию. Положительные и отрицательные сценарии исполняются на runtime.
- **AC-D2:** `managed-call` после restore продолжает прежний child ID и сохранённый результат; повторное восстановление не создаёт нового ребёнка; pause не становится timeout. Подмена child/result pin отвергается.
- **AC-D3:** `input-only` принимает объявленный ввод только в активном допустимом состоянии; отвергнутый ввод не появляется при последующем подходящем состоянии, в том числе после restore; синтетического request/result нет.
- **AC-D4:** restore отказывается при несовпадении закреплённого `contract_id` или `artifact_id`, без fallback на «последнюю совместимую» сборку и без изменения snapshot. Совпадающие pins восстанавливаются, старые экземпляры не переинтерпретируются.
- **AC-D5:** dedup key точно `(tenant, instance_id, trusted producer_id, event_id)`; одинаковый ID разных trusted producers не смешивается; другой contract при прежнем ключе даёт conflict, не новое событие. Изменения адресата/корреляции/preconditions/typed data меняют fingerprint; новый RPC ID/время доставки — нет. Те же пробы после restore; права на повтор проверяет E тестовым trusted context, без production-аутентификации.

Последовательность зависимостей: A → B → C → D → E → F; G зависит от замороженной целевой формы B/C и доступности владельца данных; H — после всех включённых в scope результатов. До приёмки C автор D может готовить только отдельные тестовые harness, не менять ядро по незавершённому интерфейсу. Безопасно параллельны A с подготовкой независимых тестовых harness; G с D–F только если отдельные авторы и раздельные файлы/репозитории; документация acceptance можно готовить параллельно без правки runtime. B/C/D/E/F не делят runtime-файлы между авторами: таблица owners выше является обязательным правилом раздачи, а при пересечении автор общего файла один, соседние задачи ждут его интерфейса.

## Гейты и достаточность выпуска

**Для `0.29.0-alpha.1`:** включены только завершённые A–D и те части E/F/G, для которых явно определены реально работающие ограничения. Обязательны runtime codec encode/decode, compiler manifest/identity, runtime lifecycle tests и хотя бы один локальный end-to-end путь без заявления долговечности, если её нет. Список включённых и не включённых capabilities, команды тестов, известные ограничения и версия артефакта зафиксированы в prerelease notes. Если эти условия не готовы — alpha не создаётся.

**Для `0.29.0`:** дополнительно завершены все дочерние результаты, объявленные владельцем обязательными для final scope; миграция тех файлов, которые включены в поддержку; для каждого заявленного host boundary — conformance; сквозной тест на влитом коде; независимая проверка новой сессией; воспроизводимая сборка и явное разрешение владельца. Production auth, durable store или сетевой binding остаются вне scope, пока их отдельно не выбрали; без них выпуск не называет себя production-ready и не обещает их гарантии.

Сквозные AC, проверяемые на влитой вершине с привязанными к SHA логами и артефактами:

- **AC-E1:** реальная машина → проверенная компиляция → manifest → typed encode/decode → local submit → receipt/applied; неправильный тип reply оставляет запрос открытым, последующий правильный reply проходит.
- **AC-E2:** человек до admission агента и после accepted до commit; неверный кандидат/устаревшие версии не меняют snapshot; после commit человек отвергается, включая паузу и старое continue против нового pause ID.
- **AC-E3:** snapshot → новый runtime instance → restore → dedup/status; identical retry не добавляет переход/intent, conflict отвергается; все AC-D1–AC-D5 воспроизводятся на включённых в scope профилях, чужой artifact останавливает restore; fault injection на каждой поддержанной границе commit/dispatch не даёт ложного успеха эффекта.
- **AC-E4:** миграция согласованного набора → повторная миграция без diff → compile/run на целевой версии; старые формы отвергаются с подсказкой; release version и список capabilities совпадают со сборкой.

**Разработка эпика принимается** не по числу задач: проверяющий воспроизводит AC-E1–AC-E4 и сверяет артефакты с выбранным scope. Сам **план** принимается отдельно: независимая проверка новой сессией exact snapshot, устранение её блокеров, затем решение владельца. В рамках подготовки плана нет merge/push/релиза, а интеграция будущих дочерних идёт только по отдельным поручениям.

## Открытые решения до заведения дочерних задач

1. Утвердить минимальный scope alpha и обязательный final scope; последствия нерешённого scope — alpha/final блокируется, либо конкретная возможность явно не поддерживается.
2. Проверить наличие/версию Nova, JSON parser/formatter, build tooling и миграционных данных. На текущей базе/записи 017 Nova отсутствовала; это наблюдение не считать актуальным без проверки в целевом worktree.
3. Выбрать, нужен ли durable backend в данном эпике. Если нет, сохранить только интерфейс и in-memory доказательства и явно исключить durable/production claims; если да — отдельное решение о backend, его транзакциях, retention, recovery и авторизации до оценки задачи.
4. Определить, какие именно машины Методики и кто вправе принять их миграцию. Не переносить данные соседнего host-продукта и не включать сетевые adapters по умолчанию.

Открытые решения не являются приглашением повторно проектировать принятые контракты; фиксировать только последствия для включения/исключения результата.
