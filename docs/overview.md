# Как работает Алула

**Пояснение, не норма.** Этот файл ничего не определяет. Единственное определение языка — [state-machine-alula-spec.md](state-machine-alula-spec.md) (версия 2.22); при расхождении прав он. Ссылки «раздел N» ниже ведут в него.

**Алула** — табличная запись стейт-машины. Машина — это состояния, строки переходов и данные. Работу в ней делают стороны: агент, человек, вложенная машина. Человек и агент — равные стороны: оба получают запрос и дают типизированный ответ (раздел 1, «`## Стороны`»).

![Как работает Алула: файл, переводчик, дерево JSON, интерпретатор, журнал, сверка со сценарием](alula-diagrams/alula-pipeline.svg)

## Шаги

**Файл машины.** Markdown-файл `*.alula.md`: шапка, затем разделы `## Типы`, `## Данные`, `## Стороны`, `## Состояния`, `## Концы` и другие, по порядку раздела 1. Файл пишется по-русски или по-английски (`- language: en`); слова двух форм — в [таблице слов](alula-keywords.tsv) (раздел 1а).

**Переводчик и проверки.** Переводчик разбирает файл и проверяет его: типы, имена, исчерпание развилок, кто пишет данные (раздел 10). Ошибка проверки — машина не собирается.

**Дерево `machine/2`.** Результат перевода — дерево JSON `<имя>.alula.json` (раздел 6). Это та же Алула в исполняемом виде, а не другой формат. Дерево одинаково для русского и английского файла: слова обоих языков дают одни ключи (раздел 1а). Имена в дереве — JSON-имена: строятся автоматически или задаются разделом `## Имена`. Схемы дерева и сценария лежат в [nv-lang/nova-alula, `src/machine/schema/`](https://github.com/nv-lang/nova-alula/tree/main/src/machine/schema).

**Интерпретатор.** Исполняет дерево. Стороне он шлёт запрос и ждёт ответ: виды сторон — `agent`, `human`, `enhanced`, вратарь (`human или agent по настройке`), `machine` (раздел 1). Всё, что машина делает с внешним миром, — примитивы хозяина (раздел 7). Класс примитива говорит, где его можно звать:

| Класс | Что делает |
|---|---|
| `pure` | чистая функция |
| `reading` | читает объект, хранилище, время; данные машины не меняет |
| `writing` | пишет внутри фиксации шага |
| `irreversible` | внешнее действие без отката; последним этапом фиксации |

**Журнал.** Каждый шаг пишет события журнала: код и параметры-тексты (тип `СобытиеЖурнала`, раздел 2; действия — раздел 5).

**Сценарий и сверка.** Сценарий `scenario/0` (`<имя>.scenario.test.json`) — события и ожидание: состояние, журнал, часть данных, очередь. Прогон сравнивает их с тем, что дал интерпретатор (раздел 11).

## Из чего состоит машина

![Из чего состоит машина: что хранит, как ходит, с кем говорит; снаружи хозяин, журнал и сценарий](alula-diagrams/alula-entities.svg)

**Типы.** Записи и перечисления, в том числе перечисления с полями (`## Типы`). Нужны, чтобы проверка знала поля входа, запроса, ответа и данных. С ними работают все остальные части. Раздел 2; подробно — [alula-data-types.md](alula-data-types.md).

**Данные.** Память машины: таблица `## Данные` с типом, начальным значением, границей `не убывает` и владельцем `пишет`. Живут весь экземпляр, переживают паузу и перезапуск. Их читают запросы и условия, меняют действия переходов. Раздел 2, «Данные» и «Время жизни данных».

**Вход.** Что дали машине при старте (`## Вход`). Не меняется; из него `начальное` собирает данные. Раздел 1.

**Состояния.** Четыре вида (раздел 4): **обращение** — ждёт ответа стороны (4.2); **операция** — делает шаг сразу (4.5); **развилка** — выбирает путь по условиям (4.6); **конец** — даёт ответ вызова: `Ответ` или `Отказ` (4.7, `## Концы`).

**Переходы.** Строки таблицы состояния: `№`, событие, условие, действия, «Куда». Событие — ответ, сбой, сигнал, `сразу`; действия меняют данные и пишут журнал. Разделы 4.3, 5.

**Функции.** Чистые вычисления автора (`## Функции`), класс `pure`. Зовутся из выражений, данные не меняют. Разделы 8, 12 (каталог встроенных).

**Стороны.** Кто делает работу (`## Стороны`): `agent`, `human`, `enhanced`, вратарь (`human или agent по настройке`), вложенная машина `machine`. У стороны — тип результата `итог`. Обращение шлёт стороне запрос и ждёт ответ. Раздел 1.

**Ворота.** Сторона `human` со счётчиком — ворота: человек решает сигналом из столбца «сигналы» (ответ типа `ИсходВорот`). Идентификатор запроса — `<идентификатор>-<номер>`; отметка «принято» у ворот хранится с состоянием машины, поэтому ответ принимается один раз. Раздел 1 (правило 19), раздел 2, «Время жизни данных».

**Фрагмент.** Готовый кусок машины в своём файле (`fragment`): параметры, данные, общие события, состояния. Подключается в `## Подключения` и подставляется в машину; пример — «Пауза» с состоянием ПАУЗА. Раздел 9.

**Хозяин.** Даёт примитивы — всё, что касается внешнего мира: время, объекты, эффекты. Классы `pure`, `reading`, `writing`, `irreversible` задают, где примитив можно звать. Раздел 7.

**Журнал.** След каждого шага: события с латинским кодом и параметрами-текстами (`СобытиеЖурнала`). Пишется в фиксации шага. Разделы 2, 5; [state-machine-journal.md](state-machine-journal.md).

**Сценарий.** `scenario/0`: события и ожидание — состояние, журнал, часть данных, очередь. Прогон сверяет их с исполнением. Раздел 11.

**Как они взаимодействуют на одном шаге.** Обращение по таблице «Запрос» собирает из данных запрос стороне. Сторона отвечает значением своего `итог`. Строка перехода ловит ответ образцом, проверяет условие и выполняет действия: меняет данные, зовёт примитивы хозяина, пишет журнал. Затем машина идёт в состояние из «Куда». Разделы 4.2, 4.3, 5, 7.

## Как исполняется машина

Ниже — один ход «Шага агента» по самому короткому пути: агент ответил `Закончен`, форма ответа верна, остановки нет. Участники — столбцы схемы: **вызывающий** (хозяин или машина-родитель, правило 35 [спецификации машин](state-machine-spec.md)), **исполнитель** (интерпретатор, правило 8), **машина** (таблицы файла), **состояние** (то, что исполнитель сохраняет: данные, очередь, открытые запросы) и **сторона** (здесь агент). Стрелка приходит туда, откуда делается следующий ход; пунктир — возврат. «Правило N» — правило [state-machine-spec.md](state-machine-spec.md), «раздел N» — раздел [спецификации Алулы](state-machine-alula-spec.md). Строки образца — [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md) (на GitHub — с номерами строк).

![Как исполняется машина: вызывающий, исполнитель, таблицы машины, сохранённое состояние и сторона; шаги 1–13](alula-diagrams/alula-sequence.svg)

1. **Запустить.** Вызывающий отдаёт исполнителю запрос с входом машины (правило 35, пункт 1). Кто: вызывающий. В файле — поля входа:
   ```
   | имя | тип | примечание |
   |---|---|---|
   | вид | ВидВызывающего | вид вызывающего |
   | профиль | ПрофильАгента | профиль агента; у вызывающего — столбец `профиль` его «Сторон» |
   | сессия | строка | сессия агента |
   | вид_диалога | строка | вид диалога |
   | контекст | строка | контекст хода |
   | пределы | ПределыАгента | пределы шага |
   | трасса | строка | трасса вызывающего |
   | номер_шага | число | номер шага вызывающего |
   ```
   (стр. [95–104](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L95-L104) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

2. **Создать экземпляр.** Исполнитель заводит экземпляр: каждое данное получает значение `начальное` (здесь `запрос_агента` собирается из входа), текущее состояние — начальное, СТАРТ (раздел 2, «Время жизни данных»; раздел 4.1). Трассу и идентификатор запроса вызова (`запрос_вызова`) даёт исполнитель, в файле их нет (правило 31; стр. 106 образца). Кто: исполнитель. В файле:
   ```
   | имя | тип | начальное | не убывает | пишет |
   |---|---|---|---|---|
   | запрос_агента | ЗапросАгента | ЗапросАгента { вид: вход.вид, профиль: вход.профиль, сессия: вход.сессия, вид_диалога: вход.вид_диалога, контекст: вход.контекст, пределы: вход.пределы, трасса: вход.трасса, номер_шага: вход.номер_шага } | — | строки |
   ```
   (стр. [112–114](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L112-L114) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

   ```
   Начальное состояние: СТАРТ
   ```
   (стр. [241](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L241) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

3. **СТАРТ, строка 1.** Первый шаг начинается с события «старт» (правило 31). СТАРТ — операция: «При входе» берёт время примитивом хозяина `time_now` (класс `reading`, стр. 424), затем строка `сразу` меняет данные и ведёт в ХОД_АГЕНТА. `сразу` — не событие извне, а переход операции сразу после работы «При входе» (раздел 4.3; правило 26). Кто: исполнитель по таблице машины, время — хозяин. В файле:
   ```
   ### СТАРТ — операция
   - При входе: пусть момент = вызвать(time_now)

   | № | Событие | Условие | Действия | Куда |
   |---|---|---|---|---|
   | 1 | сразу | — | начато = момент; число_ходов = 1 | ХОД_АГЕНТА |
   ```
   (стр. [243–248](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L243-L248) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

4. **Фиксация шага.** Шаг идёт до первого обращения: ХОД_АГЕНТА ждёт события, поэтому шаг кончается. Всё, что шаг изменил, записывается одной фиксацией: данные, строки журнала, `состояние` = ХОД_АГЕНТА, счётчик попыток агента `попытка_агента` + 1 и запрос в `открытые_запросы` («запрос открыт»); незавершённый шаг откатывается (правила 13, 15). Идентификатор запроса — идентификатор стороны и номер попытки: `agent-1` (правило 15; раздел 1, столбец `идентификатор`). Кто: исполнитель. В файле самой фиксации нет — это механика исполнителя; видны только сторона и её счётчик (`пишет: механика`):
   ```
   | агент | agent | agent(итог ИтогХода) | — | — | попытка_агента |
   ```
   (стр. [139](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L139) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

   ```
   | попытка_агента | число>=0 | 0 | да | механика |
   ```
   (стр. [129](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L129) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

5. **Запрос стороне.** После фиксации исполнитель отправляет запрос; перед отправкой он смотрит в очередь: если там «стоп человека» или «отмена_запроса», запрос не уходит (правило 13). Запрос несёт идентификатор запроса, номер попытки, сторону, конверт трассировки и поля таблицы «Запрос» с `читает: сторона` (правило 15; раздел 4.2). Поле `расход` (`читает: исполнитель`) в запрос не идёт: его читают строки состояния. «Срок тишины» вычисляется при входе, после «Запроса»; по нему исполнитель сам порождает «нет ответа» (раздел 4.2; правила 13, 16). Как запрос доходит до агента, машина не знает (правило 20). Кто: исполнитель; работает сторона. В файле:
   ```
   ### ХОД_АГЕНТА — обращение
   - Сторона: агент
   - Срок тишины: срок_хода(запрос_агента, ход, число_повторов)
   - Возвратов формы: 0
   - Запрос:

   | поле запроса | выражение | читает |
   |---|---|---|
   | запрос_агента | — | сторона |
   | ход | — | сторона |
   | число_повторов | — | сторона |
   | ход_до_повтора | — | сторона |
   | решение_разрешения | — | сторона |
   | расход | — | исполнитель |
   ```
   (стр. [250–263](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L250-L263) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

6. **Ответ стороны.** Агент отвечает значением своего типа `итог` — здесь формой `Закончен` (раздел 1, «`итог`»). Кто: сторона. В файле — тип ответа:
   ```
   тип ИтогХода перечисление
     | Закончен { текст ?строка, артефакт ?строка, расход РасходТранспорта }
     | Обрезан { расход РасходТранспорта }
     | ПределЗапросов { расход РасходТранспорта }
     | МодельОтказалась { расход РасходТранспорта }
     | Отменён { расход РасходТранспорта }
     | ВременнаяОшибка
     | ПостояннаяОшибка
     | НужноРазрешение { запрос_разрешения ЗапросРазрешения }
   ```
   (стр. [53–61](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L53-L61) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

7. **Принять; событие в очередь.** Ответ принимается при приходе: исполнитель проверяет, что запрос открыт и ещё не принят, и форму ответа; затем одной фиксацией пишет идентификатор в `принятые_запросы`, выполняет «При приёме» состояния и кладёт событие в очередь (правило 14). Принятый ответ переживает паузу и перезапуск (правило 14). Кто: исполнитель. В файле этого нет — механика; у ХОД_АГЕНТА нет и «При приёме»:
   ```
   «При приёме» у обращения нет (в коде `on_accept` пуст). Исправление формы идёт не возвратом в том же запросе, а новым ходом «fix» по строкам ПРОВЕРКИ_ОТВЕТА, поэтому `Возвратов формы: 0`. Код сбоя вне списка строки 9 исполнитель приводит к `НетРезультата`, оно в списке.
   ```
   (стр. [277](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L277) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

8. **ХОД_АГЕНТА, строка 1.** Новый шаг: исполнитель берёт из очереди первое событие, которое ждёт текущее состояние (правило 13), и ищет первую подходящую строку (раздел 4.1). Образец `ответ: Закончен { … }` привязывает поля ответа; привязки живут один шаг (раздел 2, «Время жизни данных»). Переход закрывает запрос: идентификатор уходит из `открытые_запросы` и `принятые_запросы` (правило 14). Кто: исполнитель по строке машины. В файле:
   ```
   | № | Событие | Условие | Действия | Куда |
   |---|---|---|---|---|
   | 1 | ответ: Закончен { текст, артефакт, расход: полученный } | — | расход = сложить_расход(расход, полученный); текст_ответа = текст; артефакт_ответа = артефакт | ПРОВЕРКА_ОТВЕТА |
   ```
   (стр. [265–267](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L265-L267) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

9. **ПРОВЕРКА_ОТВЕТА, строка 1.** Тот же шаг: развилка не ждёт события (правило 9). «При входе» зовёт примитив хозяина `reply_validation` (класс `reading`, стр. 425); строка 1 ведёт в УЧЁТ. Кто: исполнитель, проверку формы — хозяин. В файле:
   ```
   ### ПРОВЕРКА_ОТВЕТА — развилка
   - Читает: число_возвратов, текст_ответа, артефакт_ответа, запрос_агента
   - При входе: пусть проверка = вызвать(reply_validation)

   | № | Условие | Действия | Куда |
   |---|---|---|---|
   | 1 | проверка == ПроверкаОтвета.Верна | — | УЧЁТ |
   ```
   (стр. [298–304](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L298-L304) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

10. **УЧЁТ, строка 1.** Тот же шаг: операция собирает запись расхода и пишет её в журнал; строка `сразу` ведёт в ИТОГ_ШАГА. Кто: исполнитель, время — хозяин. В файле:
    ```
    ### УЧЁТ — операция
    - Читает: запрос_агента, остановка, расход, начато
    - При входе:
      - пусть сейчас = вызвать(time_now);
      - пусть собранное = собрать_использование(запрос_агента, остановка, расход, начато, сейчас)

    | № | Событие | Условие | Действия | Куда |
    |---|---|---|---|---|
    | 1 | сразу | — | использование = собранное; журнал(событие_расхода(собранное)) | ИТОГ_ШАГА |
    ```
    (стр. [354–362](https://github.com/unitcraft/ai-dev-methodology/blob/main/state-machines/state-machine-agent-step.alula.md#L354-L362) образца [state-machine-agent-step.alula.md](state-machine-agent-step.alula.md))

11. **ИТОГ_ШАГА, строка 1.** Тот же шаг: `остановка` пуста — переход в КОНЕЦ. Кто: исполнитель. В файле:
    ```
    ### ИТОГ_ШАГА — развилка
    - Читает: остановка
    ```

«Вызывающий» и «Состояние» на схеме — упрощения рисунка: вызывающий — хозяин или машина-родитель (правило 35); «состояние» — то, что сохраняется вместе с состоянием машины, и технические хранилища (правила 13, 14, 21–23).

**Где в этом ходе происходит запись** (пунктирные рамки на схеме):

| Шаг диаграммы | Что записывается | Когда | Правило |
|---|---|---|---|
| 2. создать экземпляр | начальное состояние СТАРТ, данные со значением `начальное` (в том числе из входа) | при запуске | раздел 2, «Данные» и «Время жизни данных»; правило 22 (сохраняется вместе с состоянием) |
| 4. цепочка СТАРТ → ХОД_АГЕНТА | данные `начато`, `число_ходов`; `состояние` = ХОД_АГЕНТА; счётчик попыток стороны; запрос в `открытые_запросы` | одной фиксацией, до отправки запроса | правила 13, 15, 16 |
| 7. приём ответа | идентификатор в `принятые_запросы`; «При приёме» состояния (у ХОД_АГЕНТА его нет); событие в очередь | одной фиксацией, при приходе ответа | правило 14 |
| 12. цепочка ХОД_АГЕНТА → ПРОВЕРКА_ОТВЕТА → УЧЁТ → ИТОГ_ШАГА → КОНЕЦ | действия строк цепочки, строки журнала, `состояние` = КОНЕЦ, закрытие запроса | одной фиксацией, после цепочки | правила 13, 14, 16 |
| 12, если есть | необратимые действия во внешнем мире (`вызвать` класса `irreversible`) | последним этапом фиксации, повторяемым без вреда | правило 13; разделы 5, 7 |

Шаги 8–11 на схеме только читают таблицы машины: действия их строк выполняются по порядку, каждое видит результат предыдущих (раздел 5), а записываются все вместе одной фиксацией на шаге 12. Шаг, упавший посреди цепочки, откатывается целиком, поэтому повторный вход в операцию или развилку безопасен (правила 12, 13).

**Что выполняет исполнитель, что хозяин, что сторона.** Исполнитель ведёт шаги, очередь событий и фиксацию, принимает ответ и проверяет его форму, следит за сроком и сам порождает «нет ответа» (правила 13–16). Хозяин даёт транспорт и примитивы: как запрос доходит до стороны, машина не знает (правило 20; примитивы — раздел 7). Сторона даёт только свой ответ на свой запрос (правило 15).

**Чего в файле нет.** Фиксация шага, очередь событий, «запрос открыт» (`открытые_запросы`), «принято» (`принятые_запросы`), счётчики попыток, трасса и номер шага — механика исполнителя: правила 13 (шаг и фиксация), 14 (приём), 15 (запрос, идентификатор, счётчик), 22 (перезапуск и конец). Их не пишут ни строки, ни «При входе»; сколько они живут — раздел 2, «Время жизни данных»: данные машины и данные исполнителя живут весь экземпляр и переживают паузу и перезапуск, привязки события — один шаг.

**Другие случаи.**

- **Срок вышел.** Исполнитель по таймеру порождает событие `сбой` с причиной `НетОтветаВСрок` (правила 13, 16). Его ловит строка ХОД_АГЕНТА 9: `остановка` = `"timeout"`, дальше УЧЁТ, ИТОГ_ШАГА 2, ОСТАНОВЛЕНО и строка «Концов» ОСТАНОВЛЕНО 5 — `Отказ(КодСбоя.НетОтветаВСрок, остановка)`.
- **Чужой ответ.** Ответ на запрос, который не открыт (неизвестный идентификатор, закрытый или отменённый запрос, повторная доставка), исполнитель записывает в журнал и отбрасывает; состояние не меняется (правило 17).
- **Стоп человека.** Общее событие ОБЩ 1 фрагмента «Пауза» (подключение — стр. 233–237 образца; строки — раздел 9): журнал, `предыдущее` = состояние, отмена открытых запросов без принятого ответа, переход в ПАУЗУ. В ПАУЗЕ «продолжить» ведёт повторным входом в `предыдущее`, «остановить» — в ОСТАНОВЛЕНО с `остановка` = `"pause_halt"` (правило 23).

**Перезапуск.** Открытые запросы, принятые запросы, счётчики, очередь и данные сохраняются с состоянием машины. После перезапуска исполнитель входит заново в сохранённое `состояние` (обращение или конец, правило 12); машина на Алуле так входит всегда: данных «в памяти» в ней нет (раздел 2, «Данные «в памяти»»). Запросы без принятого ответа, кроме запросов к вложенным машинам, отменяются, повторный вход в обращение отправляет новый запрос с новым номером попытки; принятый ответ остаётся в очереди и разбирается (правила 12, 14, 18, 22).

**Конец.** Машина отвечает ровно один раз — по таблице «Концы»: у каждого конца и каждого значения `остановка` есть строка с ответом, у отказа — с кодом (правило 35, пункт 2; раздел 4.7). У «Шага агента» строк «Концов» 13: КОНЕЦ 1, ОШИБКА 1, ОСТАНОВЛЕНО 11 (стр. 398–416 образца).

- `### ХОД_АГЕНТА — обращение` — имя состояния и вид (раздел 4.1).
- `- Сторона: агент` — кому шлётся запрос; сторона объявлена в `## Стороны` (стр. 139): вид `agent(итог ИтогХода)`, идентификатор `agent`, счётчик `попытка_агента`.
- `- Срок тишины: …` — сколько ждать ответа; выражение — функция автора `срок_хода` (стр. 203–207): у хода `"retry"` к сроку добавляется пауза повтора; нет срока в пределах — `0`, то есть срока нет. Вычисляется при входе, до отправки (раздел 4.2).
- `- Возвратов формы: 0` — сколько раз исполнитель возвращает агенту ответ не по форме в том же запросе; здесь ни разу: исправление формы идёт новым ходом `"fix"` через ПРОВЕРКУ_ОТВЕТА (стр. 277).
- `- Запрос:` и таблица — поля запроса. `—` в столбце «выражение» — то же имя (AL-56). `читает: сторона` — поле уходит агенту; `читает: исполнитель` — поле читают строки состояния, агенту оно не уходит (`расход`: строки 1–5 прибавляют к нему полученный расход). Профиля в таблице нет: он внутри `запрос_агента.профиль` (стр. 145).
- Таблица строк: `№` — номер строки; «Событие» — образец ответа или `сбой`; «Условие» у строк обращения — `—` (раздел 4.2); «Действия» — через `;` в порядке записи (раздел 5); «Куда» — следующее состояние.
- `ответ: Закончен { текст, артефакт, расход: полученный }` — форма `Закончен` типа `ИтогХода`; поля `текст`, `артефакт` привязаны под своими именами, поле `расход` — под именем `полученный`: привязка с именем данного `расход` была бы ошибкой (раздел 4.3, AL-26).
- `ответ: ВременнаяОшибка`, `ответ: ПостояннаяОшибка` — формы без полей, без скобок (раздел 4.3).
- `сбой(причина в […])` — отказ или «нет ответа» с кодом из списка; код вне списка исполнитель приводит к `НетРезультата` (раздел 4.3; правило 16; стр. 277).
